# 3.3 登录模块技术方案

> 本文描述 Web、移动端及前后端分离应用中身份认证系统的通用技术实现。重点覆盖输入验证、邮箱验证码、密码安全、会话与令牌、接口鉴权、权限控制、OAuth 2.0/OIDC、账号恢复及安全防护。本文不限定具体业务、数据库结构或邮件服务商。

---

## 一、设计原则与安全边界

身份系统需要分别解决以下问题：

- **身份识别（Identification）**：用户声明自己是谁，例如提交邮箱、用户名或第三方账号。
- **身份认证（Authentication）**：系统验证该身份声明，例如校验密码、邮箱验证码、Passkey 或第三方身份令牌。
- **会话管理（Session Management）**：认证成功后，系统在有限时间内持续识别该用户。
- **权限判定（Authorization）**：系统判断当前用户能否访问某个资源或执行某项操作。
- **账号恢复（Account Recovery）**：用户丢失密码或认证设备后，通过可信渠道恢复账号。
- **审计与风控（Audit & Risk Control）**：记录安全事件，识别暴力破解、撞库、验证码轰炸和账号接管行为。

认证通过不等于拥有业务权限。客户端页面隐藏、路由守卫和按钮禁用只用于改善体验，最终权限必须由服务端根据当前身份和目标资源重新判定。

面向真实用户的生产认证流量必须使用 HTTPS。受控的本地或短期测试环境可以使用 HTTP，但必须通过独立环境配置关闭 Cookie 的 `Secure` 属性，且不得承载生产账号或敏感数据。生产环境应启用 HSTS，禁止密码、验证码、OAuth 授权码、访问令牌和刷新令牌出现在 URL 查询参数、访问日志、分析平台或异常堆栈中。

## 二、标识符与输入验证

### 2.1 标识符规范化

邮箱作为登录标识时，应在注册、登录、发送验证码和找回密码等所有入口采用一致的规范化逻辑：

```text
去除首尾空白 -> 校验长度与格式 -> 域名部分转小写 -> 保存规范化结果
```

通常可将完整邮箱转为小写，以获得稳定的唯一性判断；如果业务必须兼容邮箱本地部分大小写，应同时保存原始展示值和规范化索引值。不要擅自删除 `+tag`、点号或改写不同邮箱服务商的特殊地址规则。

用户名应明确允许的字符集、最小/最大长度和大小写规则，并在数据库唯一约束之外进行应用层校验。所有唯一性最终仍以数据库约束为准，避免并发注册绕过“先查询、后创建”的检查。

### 2.2 服务端为最终校验方

前端校验只用于即时反馈，服务端必须重新校验：

- 字段类型、必填项和长度；
- 邮箱、用户名、验证码等格式；
- 密码策略；
- 枚举值和业务状态；
- 请求体大小和未知字段；
- 唯一性、验证码状态和权限条件。

推荐使用 JSON Schema、Zod、Joi、Valibot 或框架自带验证器集中维护请求契约。拒绝类型强制转换带来的歧义，例如不要把数组、对象或数字隐式转换为用户名或邮箱。

### 2.3 错误信息策略

注册时可以明确提示邮箱已被使用，便于正常用户处理；在登录、找回密码和验证码重发等容易被用于枚举账号的接口中，应统一外部响应：

```text
如果账号存在且满足条件，我们将发送邮件。
```

服务端日志可以保留内部失败原因，但不得记录密码、明文验证码、完整令牌或 OAuth 客户端密钥。

## 三、邮箱验证码认证

### 3.1 适用场景

邮箱验证码可用于：

- 注册邮箱所有权验证；
- 修改绑定邮箱；
- 找回密码前的身份确认；
- 高风险操作的二次确认；
- 无密码登录（需采用比注册验证更严格的风控）。

每个验证码必须绑定具体用途，注册验证码不得用于重置密码或修改邮箱。建议使用明确的 purpose，例如 `REGISTER`、`RESET_PASSWORD`、`CHANGE_EMAIL`、`LOGIN`。

### 3.2 验证码生成

六位数字验证码必须使用密码学安全随机数生成器：

```ts
import crypto from 'node:crypto'

const code = crypto.randomInt(0, 1_000_000).toString().padStart(6, '0')
```

不得使用 `Math.random()`、时间戳、用户 ID 截断值或可预测序列。

六位数字只有一百万种组合，不能仅依赖普通 SHA-256 防止离线穷举。服务端应使用仅保存在密钥管理系统或环境变量中的独立密钥计算 HMAC：

```text
codeDigest = HMAC-SHA-256(
  EMAIL_CODE_SECRET,
  normalizedEmail + ":" + purpose + ":" + challengeId + ":" + code
)
```

持久层只保存摘要，不保存明文验证码。`EMAIL_CODE_SECRET` 必须与 JWT、Cookie 和 OAuth 密钥相互独立。

### 3.3 发送流程

推荐的发送流程为：

```text
客户端提交邮箱和用途
-> 服务端规范化并校验邮箱
-> 检查账号状态和限流
-> 使该邮箱同用途的旧验证码失效
-> 生成 challengeId、验证码和摘要
-> 保存摘要、有效期及尝试次数
-> 调用邮件服务商
-> 返回 challengeId、有效时长和可重发时间
```

接口不得向客户端返回明文验证码。开发环境如需查看验证码，应使用受控的本地邮件捕获器；不要在生产代码中保留“万能验证码”或通过日志输出验证码。

建议默认策略：

- 验证码有效期：10 分钟；
- 同一邮箱重发间隔：60 秒；
- 同一验证码最多失败：5 次；
- 同一邮箱每小时发送上限：5 次；
- 同一 IP 每小时发送上限：20 次；
- 新验证码生成后，同用途旧验证码立即失效；
- 验证成功后立即标记为已使用，禁止重放。

阈值应根据真实流量、用户地区和风险数据调整，不能只依赖单一 IP，因为共享网络、代理和 IPv6 可能造成误伤或绕过。

### 3.4 校验与注册提交

验证码校验应同时检查：

1. `challengeId` 是否存在；
2. 邮箱和 purpose 是否与 challenge 绑定信息一致；
3. 是否未过期、未使用、未被新 challenge 替代；
4. 错误次数是否未超过上限；
5. HMAC 摘要是否使用常量时间比较匹配。

最终注册接口必须再次校验验证码，不能信任前端的“验证成功”状态。用户创建与验证码消费应在同一事务内完成，防止同一验证码并发创建多个账号。

可采用两种交互方式：

- **注册时直接校验**：注册接口接收 `challengeId + code`，校验成功后创建账号；实现简单，适合大多数产品。
- **先验证后注册**：验证码校验成功后签发一个短时、单用途的 `verificationGrant`，注册接口消费该凭证；适合多步骤注册，但凭证必须绑定邮箱、用途和过期时间，并保证一次性消费。

### 3.5 邮件发送层

邮件能力应封装为服务商无关接口：

```ts
interface TransactionalMailProvider {
  sendVerificationCode(input: {
    to: string
    code: string
    purpose: string
    expiresInMinutes: number
    locale?: string
  }): Promise<{ providerMessageId: string }>
}
```

底层可以使用 SMTP、Amazon SES、阿里云邮件推送、Resend 或其他事务邮件 API。SMTP 客户端库只是传输工具，不等同于邮件服务商。

生产环境应完成 SPF、DKIM、DMARC 配置，使用独立的事务邮件子域名，并处理退信、投诉和服务商限流。邮件发送失败时，不应把 challenge 视为已成功送达；应记录可重试状态，但避免无界自动重试造成重复邮件。

邮件正文应包含用途、有效时间、安全提醒和品牌信息，不应包含密码或其他敏感资料：

```text
你的验证码是 123456，10 分钟内有效。
如非本人操作，请忽略本邮件。请勿向任何人泄露验证码。
```

## 四、密码认证与加密

### 4.1 密码策略

推荐允许 8～128 个字符，支持密码管理器生成的长密码、空格和 Unicode。与其强制频繁改密或复杂的字符组合，更应阻止常见密码和已泄露密码，并通过速率限制和多因素认证降低撞库风险。

不得：

- 截断用户密码而不提示；
- 通过邮件发送原密码；
- 以明文、可逆加密、MD5、SHA-1 或单次 SHA-256 保存密码；
- 在日志、埋点或错误监控中记录密码；
- 因固定周期强制用户改密，除非检测到泄露或账号风险。

### 4.2 密码哈希

新系统优先使用 Argon2id；如果运行环境、部署平台或现有技术栈更适合 bcrypt，也可以使用 bcrypt，并制定渐进升级策略。

Argon2id 参数应根据生产机器基准测试确定，使单次哈希在可接受登录延迟下尽可能昂贵。bcrypt 建议 cost 至少为 12，并注意 bcrypt 对超长输入的处理限制。

密码哈希库生成并保存随机 salt；salt 不需要保密。可额外使用应用级 pepper：

```text
passwordHash = PasswordHash(password, randomSalt, optionalPepper)
```

pepper 必须保存在 KMS、密钥托管服务或安全环境变量中，不与密码哈希存放在同一数据库。

### 4.3 登录校验

密码登录流程：

```text
规范化登录标识
-> 查询账号及认证状态
-> 对不存在的账号执行等成本的伪哈希
-> 验证密码哈希
-> 执行风控与账号状态检查
-> 必要时完成 MFA
-> 创建会话并签发令牌
-> 记录安全审计事件
```

外部错误统一为“账号或密码错误”，避免通过响应内容枚举用户。还应尽量缩小“账号不存在”和“密码错误”之间的响应时间差异。

用户成功登录时，如果发现旧哈希参数低于当前标准，应在本次请求内重新计算新哈希并更新，这称为渐进式 rehash，无需强制所有用户同时改密。

### 4.4 找回与修改密码

忘记密码应使用一次性、短时的恢复凭证，流程为：

```text
提交邮箱
-> 返回统一响应
-> 发送验证码或恢复链接
-> 验证恢复凭证
-> 设置新密码
-> 撤销该用户所有既有会话和刷新令牌
-> 发送密码已修改通知
```

登录状态下修改密码时，应要求当前密码或近期重新认证。管理员不得查看或设置用户明文密码；如需协助，只能触发受控的重置流程。

## 五、会话、Cookie 与令牌

### 5.1 两种主流方案

服务端会话适合传统 Web：浏览器只保存不可预测的 session ID，服务端保存会话状态，便于即时撤销和集中控制。

Access Token + Refresh Token 适合前后端分离、多客户端或 API 场景：

- Access Token 生命周期短，用于访问 API；
- Refresh Token 生命周期较长，只用于换取新令牌；
- 服务端保存刷新令牌摘要、会话状态、设备信息和撤销状态；
- 每次刷新执行 Refresh Token Rotation，旧令牌立即失效；
- 检测到旧刷新令牌被再次使用时，视为可能泄露并撤销整个 token family。

JWT 并不是会话管理的必选项。无法即时撤销的长寿命 JWT 不适合高风险身份系统。

### 5.2 推荐生命周期

常见默认值：

- Access Token：5～15 分钟；
- Refresh Token：7～30 天；
- 高风险操作重新认证窗口：5～15 分钟；
- 长期未活动会话自动失效；
- 密码重置、账号冻结或疑似被盗后撤销全部会话。

具体时长应根据业务风险、终端类型和用户体验确定。

### 5.3 JWT 要求

JWT 至少校验：

- 签名算法在服务端白名单中，禁止接受 `none`；
- `iss` 与预期签发方一致；
- `aud` 与当前 API 一致；
- `exp`、`nbf`、`iat` 合法；
- `sub` 是稳定的内部用户 ID；
- `jti` 可用于审计和撤销；
- 密钥 ID `kid` 只能用于选择受信任密钥，不能拼接任意文件或 URL。

JWT Payload 只是编码，不是加密。不要放入密码、验证码、身份证件、完整权限清单或其他敏感信息。角色和权限可能在令牌有效期内变化，高风险接口应查询当前服务端状态，或使用短期令牌配合会话版本号。

对多服务系统优先采用非对称签名，例如 ES256 或 RS256，由认证服务持有私钥，资源服务只持有公钥。单体应用可使用足够强的 HMAC 密钥，但必须支持密钥轮换，并将密钥与业务代码分离。

### 5.4 浏览器存储策略

浏览器应用推荐将 Refresh Token 或 session ID 放入 Cookie：

```text
HttpOnly
Secure
SameSite=Lax 或 Strict
Path 限定到必要范围
合理的 Max-Age
```

`HttpOnly` 可以降低令牌被 XSS 直接读取的风险，但不能阻止恶意脚本以用户身份发请求，因此仍需 CSP、输出编码和依赖安全治理。

如果认证依赖 Cookie，所有状态变更接口必须防御 CSRF，可使用 SameSite、CSRF Token、Origin/Referer 校验组合。不要笼统认为“使用 JWT 就天然免疫 CSRF”，是否存在 CSRF 取决于凭证是否被浏览器自动携带。

Access Token 如需由前端内存持有，应避免写入 URL、日志和持久化存储。将长期令牌放入 `localStorage` 会扩大 XSS 泄露后的影响范围。

### 5.5 登出与撤销

登出不是单纯删除客户端状态。服务端应：

1. 撤销当前会话或刷新令牌；
2. 清除认证 Cookie；
3. 记录登出事件；
4. 根据请求支持“退出当前设备”与“退出所有设备”。

短期 Access Token 可以自然过期；高风险系统可以维护撤销列表或会话版本，在每次请求时检查。

## 六、接口鉴权与权限控制

### 6.1 认证中间件

认证中间件负责：

```text
提取凭证
-> 校验格式、签名、签发方、受众和有效期
-> 查询会话是否有效
-> 检查账号是否冻结、删除或强制下线
-> 构造最小可信身份上下文
```

身份上下文可包含：

```ts
type AuthContext = {
  userId: string
  sessionId: string
  authMethods: Array<'password' | 'email_otp' | 'oauth' | 'mfa' | 'passkey'>
  authenticatedAt: number
  tenantId?: string
}
```

认证失败返回 401；身份有效但权限不足返回 403。不要使用 200 包装认证失败，也不要仅依赖客户端角色字段。

### 6.2 授权模型

常见模型包括：

- RBAC：按角色授予权限，例如管理员、编辑者、普通用户；
- ABAC：结合资源归属、租户、时间、状态等属性判断；
- ACL：针对具体资源维护主体访问列表；
- ReBAC：根据用户、组织、资源之间的关系授权。

大多数业务可以使用 RBAC 定义粗粒度能力，再通过资源归属和租户边界进行细粒度校验：

```text
允许操作 = 角色具备能力
          AND 当前用户属于资源所在租户
          AND 用户是资源所有者或具备跨资源权限
          AND 资源状态允许该操作
```

服务端应默认拒绝，权限名称采用稳定的动作语义，例如 `paper.read`、`paper.publish`，避免在各处散落 `role === "admin"`。批量接口必须逐项或按安全查询条件限制资源范围，防止 IDOR/BOLA 越权。

### 6.3 高风险操作重新认证

以下操作不应只依赖一个长期登录状态：

- 修改密码、邮箱、MFA 或 OAuth 绑定；
- 查看或导出敏感数据；
- 支付、提现和权限提升；
- 删除账号或批量管理用户。

系统应检查 `authenticatedAt` 和认证强度，必要时要求重新输入密码、验证码、Passkey 或 MFA。重新认证结果应签发短时、单用途的 step-up grant，而不是永久提高当前会话权限。

## 七、OAuth 2.0 与 OpenID Connect

### 7.1 协议定位

OAuth 2.0 是授权框架，本身不定义“用户是谁”。使用第三方账号登录时，应采用 OpenID Connect（OIDC），并验证服务商签发的 ID Token。不要把 Access Token 当作身份声明，也不要仅根据客户端提交的第三方用户信息创建会话。

对于公开客户端、SPA 和移动端，推荐 Authorization Code Flow + PKCE；不使用 Implicit Flow。机密服务端客户端还应安全保存 client secret。

### 7.2 发起授权

服务端生成并保存：

- `state`：防止登录 CSRF，并绑定发起登录的浏览器会话；
- `nonce`：绑定 ID Token，防止重放；
- PKCE `code_verifier` 和对应的 `code_challenge`；
- 登录后允许跳转的站内目标。

回调地址必须在服务商控制台精确注册。登录完成后的跳转目标只能来自站内白名单或服务端保存值，禁止直接信任用户提供的任意 `redirectUrl`，避免开放重定向。

### 7.3 回调处理

标准回调流程：

```text
接收 code 和 state
-> 常量时间校验 state，并保证单次使用
-> 使用 code + code_verifier 在后端换取令牌
-> 根据服务商元数据获取并缓存 JWKS
-> 验证 ID Token 签名、iss、aud、exp、iat、nonce
-> 读取稳定的 provider subject
-> 查找或创建本地身份绑定
-> 执行账号状态和风险检查
-> 创建本地会话
-> 清理一次性 OAuth 状态
```

本地身份的唯一键应是：

```text
provider + issuer + subject
```

不能使用昵称、头像、可变用户名或邮箱作为第三方身份的永久主键。

### 7.4 邮箱与账号关联

第三方返回邮箱时必须检查 `email_verified` 或服务商等价声明。即使邮箱已验证，也不建议在无提示的情况下自动把第三方身份绑定到现有高价值账号，因为这可能造成账号接管或服务商之间的信任边界混淆。

安全的绑定策略：

- 当前用户已登录：要求近期重新认证，再绑定新的 OAuth 身份；
- 当前用户未登录但邮箱与现有账号相同：要求登录原账号或完成额外邮箱验证后绑定；
- 没有现有账号：创建本地账号并保存第三方身份关系；
- 解绑最后一个登录方式前：要求用户先设置另一种可用认证方式。

不要仅因 OAuth 回调返回相同邮箱就静默合并账号。

### 7.5 第三方令牌处理

如果第三方令牌只用于登录，完成身份验证后通常无需长期保存。如果业务需要代表用户调用第三方 API：

- 仅申请最小 scope；
- 加密保存 refresh token；
- 对密钥和令牌实施访问隔离；
- 处理撤销、过期和 scope 变化；
- 不把第三方 refresh token 返回浏览器；
- 用户解绑时调用服务商撤销接口并删除本地令牌。

OIDC 元数据、授权端点、令牌端点和 JWKS 地址应来自服务商官方 discovery 文档或固定配置，不能由客户端请求动态指定，避免 SSRF 和恶意签发方注入。

## 八、多因素认证与无密码认证

高风险系统建议提供 MFA：

- TOTP：兼容性好，服务端加密保存种子；
- WebAuthn/Passkey：抗钓鱼能力强，推荐作为优先方案；
- 硬件安全密钥：适合管理员和高价值账号；
- 恢复码：一次性使用，只保存哈希。

短信和邮箱验证码可以作为补充或恢复渠道，但抗 SIM 换卡、邮箱被盗和钓鱼能力较弱，不应作为最高安全等级的唯一第二因素。

启用 MFA 时，应先完成一次高强度认证，再展示或绑定密钥；启用成功后生成恢复码。关闭 MFA、重新生成恢复码和新增认证器都应要求近期重新认证，并发送安全通知。

Passkey 实现需验证 challenge、origin、RP ID、签名计数及用户验证标志；challenge 必须随机、短时、单次使用，并绑定当前认证流程。

---

## 九、限流、风控与账号保护

### 9.1 分层限流

认证接口应按多个维度限流：

- IP 或可信代理解析后的客户端地址；
- 规范化账号或邮箱摘要；
- 设备/会话标识；
- 全局服务容量；
- 单个 OAuth provider 或邮件服务商配额。

登录失败可使用渐进延迟、滑动窗口和短时账号冷却。不要永久锁死账号，否则攻击者可以利用锁定机制拒绝服务。验证码发送接口还应防止邮件轰炸，并在达到阈值后返回统一结果。

多实例部署不能使用进程内计数作为唯一生产限流方案，应使用 Redis、网关或其他共享存储，并定义降级策略。

### 9.2 风险信号

可结合以下信号决定允许、拒绝或要求 step-up：

- 短时间大量失败；
- 新设备、新地区或异常自治系统；
- 不可能的地理位置切换；
- 泄露密码命中；
- Refresh Token 重用；
- 邮箱、密码、MFA 连续变更；
- OAuth provider 或 subject 异常变化；
- 管理员账号的异常登录时间和来源。

设备指纹只能作为风险信号，不能作为唯一身份凭证；应考虑隐私、误判和浏览器变化。

### 9.3 审计事件

至少记录：

- 注册、邮箱验证成功/失败；
- 登录成功/失败和采用的认证方式；
- 令牌刷新、重用检测、登出和会话撤销；
- 密码重置、邮箱修改、MFA/Passkey 变更；
- OAuth 绑定、解绑及回调失败；
- 权限拒绝、角色或高风险设置变更。

日志字段应包含时间、事件类型、结果、内部用户 ID、会话 ID、请求关联 ID、经过最小化处理的 IP/设备信息。邮箱可记录不可逆摘要或脱敏值。日志必须防篡改、限制访问并设置保留期限。

## 十、Web 安全与基础设施要求

### 10.1 XSS、CSRF 与 CORS

- 对所有输出按上下文编码，不直接渲染不可信 HTML；
- 配置严格 CSP，逐步移除 `unsafe-inline` 和不必要的第三方脚本；
- Cookie 认证必须实施 CSRF 防护；
- CORS 使用明确来源白名单，不将任意 Origin 与凭证模式同时启用；
- 校验 WebSocket/SSE 建连时的来源和身份；
- OAuth 回调和邮件链接页面不得执行不可信查询参数内容。

### 10.2 密钥管理

以下密钥必须分离：

- 密码 pepper；
- 邮箱验证码 HMAC 密钥；
- JWT/HMAC 或非对称签名密钥；
- Cookie 签名/加密密钥；
- OAuth client secret；
- SMTP 密码或邮件服务 API Key。

生产密钥放入 KMS、Secret Manager 或部署平台密钥系统，不写入代码、镜像、文档或 Git。建立密钥版本、轮换、回滚和泄露响应机制；服务启动时缺少关键密钥应直接失败，而不是使用默认值。

### 10.3 代理与网络

应用位于反向代理后时，只信任明确的代理层，避免攻击者伪造 `X-Forwarded-For` 绕过限流。认证 Cookie 只通过 HTTPS 下发，内部服务间调用使用网络隔离和服务身份，不因“内网”而跳过授权。

数据库、Redis、邮件服务和 OAuth 服务商调用都应设置连接/读取超时、有限重试、熔断与可观测性。对非幂等认证操作谨慎重试，避免重复创建会话或重复发送邮件。

## 十一、建议接口契约

接口名称可以按项目规范调整，但职责应保持清晰：

```text
POST /auth/email-codes             发送邮箱验证码
POST /auth/register                使用验证码注册
POST /auth/login/password          密码登录
POST /auth/login/email-code        邮箱验证码登录（可选）
POST /auth/token/refresh           轮换刷新令牌
POST /auth/logout                  退出当前会话
POST /auth/logout-all              退出全部会话
POST /auth/password/forgot         发起密码恢复
POST /auth/password/reset          消费恢复凭证并设置新密码
POST /auth/password/change         登录状态下修改密码
GET  /auth/sessions                查看活跃会话
DELETE /auth/sessions/:sessionId   撤销指定会话
GET  /auth/oauth/:provider/start   发起 OAuth/OIDC 授权
GET  /auth/oauth/:provider/callback 处理 OAuth/OIDC 回调
POST /auth/oauth/:provider/link    绑定第三方身份
DELETE /auth/oauth/:provider/link  解绑第三方身份
POST /auth/mfa/challenge           发起二次认证
POST /auth/mfa/verify              完成二次认证
```

发送验证码示例：

```json
{
  "email": "user@example.com",
  "purpose": "REGISTER"
}
```

```json
{
  "challengeId": "opaque-random-id",
  "expiresIn": 600,
  "resendAfter": 60
}
```

注册示例：

```json
{
  "email": "user@example.com",
  "username": "example-user",
  "password": "user-supplied-password",
  "challengeId": "opaque-random-id",
  "emailCode": "123456"
}
```

认证响应不应泄露内部异常。推荐使用稳定的业务错误码，例如：

```text
AUTH_INVALID_CREDENTIALS
AUTH_EMAIL_CODE_INVALID
AUTH_EMAIL_CODE_EXPIRED
AUTH_EMAIL_CODE_ATTEMPTS_EXCEEDED
AUTH_REAUTH_REQUIRED
AUTH_SESSION_EXPIRED
AUTH_FORBIDDEN
AUTH_OAUTH_STATE_INVALID
AUTH_OAUTH_IDENTITY_CONFLICT
AUTH_RATE_LIMITED
```

HTTP 状态语义建议：输入错误使用 400/422，未认证使用 401，权限不足使用 403，资源冲突使用 409，限流使用 429，服务商暂时不可用使用 503。错误响应应携带请求关联 ID，便于排障。

## 十二、配置示例

配置名称应表达用途，并由部署系统注入：

```env
# 邮箱验证码
EMAIL_CODE_SECRET=<独立高强度随机密钥>
EMAIL_CODE_TTL_SECONDS=600
EMAIL_CODE_RESEND_SECONDS=60
EMAIL_CODE_MAX_ATTEMPTS=5

# 事务邮件（SMTP示例）
SMTP_HOST=<服务商SMTP地址>
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=<事务邮件发信地址>
SMTP_PASS=<SMTP专用密码>
MAIL_FROM="Product Name <no-reply@mail.example.com>"

# 会话与令牌
AUTH_ISSUER=https://auth.example.com
AUTH_AUDIENCE=https://api.example.com
ACCESS_TOKEN_TTL_SECONDS=900
REFRESH_TOKEN_TTL_SECONDS=2592000
COOKIE_SECURE=true
COOKIE_SAME_SITE=lax

# OIDC Provider示例
OIDC_PROVIDER_CLIENT_ID=<client-id>
OIDC_PROVIDER_CLIENT_SECRET=<client-secret>
OIDC_PROVIDER_ISSUER=<official-issuer-url>
OIDC_PROVIDER_REDIRECT_URI=https://app.example.com/auth/callback
```

密钥不得提供可工作的默认值。布尔值、端口和时长应在启动阶段完成类型校验，生产环境发现不安全配置时拒绝启动。

同一套应用代码可以通过环境变量适配不同部署环境，推荐矩阵如下：

| 环境 | 站点协议 | Cookie Secure | Cookie SameSite | SMTP Secure | 典型用途 |
| --- | --- | --- | --- | --- | --- |
| local | HTTP | false | lax | true | 本机开发 |
| test | HTTP | false | lax | true | 受控测试服务器 |
| prod | HTTPS | true | lax | true | 生产环境 |

`Cookie Secure` 控制浏览器到业务服务的 Refresh Cookie，`SMTP Secure` 控制业务服务到邮件服务商的独立 TLS 连接，两者不能混为一谈。HTTP 测试环境下前后端应尽量使用同一主机名；如果跨站部署，现代浏览器要求 `SameSite=None` 的 Cookie 同时具备 `Secure=true`，因此跨站 HTTP 无法安全承载这类 Cookie。反向代理部署还应显式配置可信代理跳数，使真实客户端 IP、审计和限流结果准确。

## 十三、测试与上线验收

### 13.1 功能测试

- 注册、登录、登出、刷新、找回密码均覆盖成功和失败路径；
- 验证码与邮箱、用途、challenge 绑定；
- 验证码过期、重复使用、重发替换和错误次数上限生效；
- 密码修改后旧会话按策略撤销；
- OAuth state、nonce、PKCE、ID Token 验证完整；
- 第三方邮箱冲突不会静默合并账号；
- 401 与 403 语义正确；
- 资源归属、租户隔离和批量接口不存在越权。

### 13.2 安全测试

- 暴力破解、撞库、账号枚举和验证码轰炸；
- 重放验证码、恢复凭证、OAuth code 和 Refresh Token；
- JWT 算法混淆、错误 issuer/audience、过期令牌和密钥轮换；
- 登录 CSRF、普通 CSRF、XSS 后的会话影响；
- OAuth 开放重定向、账号绑定劫持和恶意 issuer/JWKS；
- IDOR/BOLA、角色伪造和跨租户访问；
- 并发注册、并发消费验证码和并发刷新令牌。

### 13.3 运维验收

- SPF、DKIM、DMARC 验证通过，退信与投诉可观测；
- 生产环境仅允许 HTTPS，Cookie 属性正确；
- 密钥位于安全存储并具备轮换方案；
- 多实例限流和会话存储一致；
- 审计日志不含密码、验证码和令牌；
- 邮件、OAuth、Redis、数据库异常有超时和告警；
- 管理员账号启用 MFA/Passkey；
- 建立账号接管、密钥泄露和邮件服务异常的应急流程。

## 十四、推荐实施顺序

```text
统一输入验证与错误码
-> 完成密码哈希和登录限流
-> 接入邮箱验证码与事务邮件
-> 建立短期 Access Token / 可撤销会话
-> 完成刷新令牌轮换和服务端登出
-> 建立 RBAC + 资源级授权
-> 实现密码恢复和安全通知
-> 接入 OIDC Authorization Code + PKCE
-> 增加 MFA/Passkey 与高风险重新认证
-> 完成审计、监控、密钥轮换和安全测试
```

身份系统应优先保证凭证不可泄露、会话可撤销、权限由服务端判定和恢复流程不可被滥用，再逐步扩展第三方登录与无密码认证。任何新增登录方式都必须纳入统一的本地账号、会话、风控、审计和撤销体系，不能形成绕过主认证策略的旁路。
