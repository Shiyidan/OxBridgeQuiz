# 银联商务聚合支付技术方案

## 一、文档目的与适用范围

本文描述通过银联商务天满服务平台接入线上聚合支付的通用技术方案，覆盖从商户开通、测试联调到生产交易、退款和对账的完整链路，并说明业务系统应如何与支付能力集成。

本文不绑定某个具体产品的会员、订单或商品逻辑。业务系统可将文中的“业务订单”替换为商品订单、服务订单、充值订单、订阅订单或其他需要收款的业务对象。

本文适用于以下场景：

- PC 网站支付
- 手机浏览器 H5 支付
- 微信公众号支付
- 微信小程序支付
- App 支付
- 由银联商务统一受理的微信、支付宝、云闪付、银行卡等支付方式

线下 B 扫 C、POS 和收银终端不作为本文主链路。若接入线下交易，还需要额外处理设备类型、终端信息和地理位置等监管字段。

> 说明：银联商务不同产品的接口地址、请求字段、认证方式和返回结构可能不同。本文定义系统架构和处理原则，实际接口参数必须以天满服务平台开发者中心当前版本的产品文档为准。

## 二、支付参与方与职责边界

### 2.1 参与方

| 参与方 | 主要职责 |
|------|---------|
| 用户端 | 选择支付方式、跳转收银台、完成付款、查看支付结果 |
| 业务前端 | 提交购买意图、展示支付入口、轮询业务系统中的订单状态 |
| 业务后端 | 生成订单、确定金额、调用银联商务、验签通知、驱动业务履约 |
| 银联商务 | 聚合支付受理、路由支付渠道、返回交易结果、提供查询和退款能力 |
| 微信/支付宝/云闪付等 | 向用户提供付款工具并完成渠道侧支付 |
| 数据库 | 保存业务订单、支付订单、通知、退款、履约和对账记录 |
| 运维及财务后台 | 查询交易、处理退款、核对结算、处置异常订单 |

### 2.2 “银联通道”的含义

采用银联商务通道不等于用户只能使用银联卡。银联商务可以作为统一的支付服务商和收单入口，在已签约并开通相应权限的前提下受理微信、支付宝、云闪付、银行卡等支付方式。

典型链路为：

```text
业务系统 → 银联商务 → 微信 / 支付宝 / 云闪付 / 银行卡网络
```

业务系统通常只需要维护一套银联商务接入层，不需要在核心业务中分别实现微信和支付宝的全部协议。但是，不同支付渠道仍可能要求不同的场景参数、应用标识和上线权限。

### 2.3 系统状态的权威来源

各系统对不同状态负责：

- 商品、服务、订阅内容由业务系统负责。
- 应付金额由业务后端负责，不能由前端决定。
- 支付受理结果由银联商务异步通知或主动查询结果确认。
- 微信、支付宝页面回跳仅用于改善用户体验，不是支付成功的最终依据。
- 发货、开通服务或增加余额等履约动作由业务系统完成。

## 三、接入前准备

### 3.1 商务及平台准备

1. 注册并登录银联商务天满服务平台企业账号。
2. 已有银联商务商户应绑定现有商户号，不要误操作为重新申请入网。
3. 向客户经理确认商户号、结算主体、费率、结算周期和退款权限。
4. 在开发者中心申请测试参数并进行自助联调。
5. 根据实际终端申请支付产品，例如 PC/H5、公众号、小程序或 App 支付。
6. 分别确认微信、支付宝、云闪付等渠道是否已签约和开通。
7. 联调通过后绑定商户并申请支付服务上线。
8. 获取生产参数，并通过受控配置系统部署到生产环境。

天满平台上线申请应按照接入指引操作。文档特别提示：申请接口上线时不要填写 IP 字段，具体仍以平台当前页面要求为准。

### 3.2 必须取得的技术资料

- 平台接入认证方式
- 测试和生产环境接口地址
- 下单、查询、关闭、退款和退款查询接口文档
- 支付通知字段、签名规则、响应格式和重试策略
- 支付产品及渠道参数说明
- 商户号、终端号、应用标识和通讯密钥
- 错误码和交易状态说明
- 账单下载或对账接口说明
- 测试账号、测试金额及测试渠道限制

### 3.3 域名与网络条件

- 银联商务测试环境允许通知地址使用公网可访问的 HTTP 或 HTTPS；因此“公网 IP + HTTP”可用于当前联调。
- 正式生产环境的业务站点和通知地址统一使用“备案域名 + HTTPS”，不继续使用裸 IP。
- 通知地址必须可被银联商务公网访问。
- 通知接口不能依赖浏览器 Cookie 或用户登录态。
- 支付返回地址和通知地址必须分别配置，不得混用。
- 生产环境应具有稳定域名，避免将临时 IP 或开发机地址作为回调地址。
- 如支付产品对备案域名、公众号域名、小程序主体或 App 包名有要求，应提前完成配置。

## 四、总体技术架构

### 4.1 推荐分层

```text
┌─────────────────────────────────────────────────────────┐
│                       业务前端                          │
│  套餐/商品页  收银台  支付结果页  订单列表  退款进度   │
└───────────────────────┬─────────────────────────────────┘
                        │ 只调用业务后端
┌───────────────────────▼─────────────────────────────────┐
│                       业务后端                          │
│  业务订单服务  支付应用服务  履约服务  管理后台接口     │
├─────────────────────────────────────────────────────────┤
│                      支付领域层                         │
│  支付订单  状态机  幂等控制  退款  通知  对账          │
├─────────────────────────────────────────────────────────┤
│                    银联商务适配层                       │
│  请求认证  报文转换  下单  查询  关闭  退款  验签      │
└───────────────────────┬─────────────────────────────────┘
                        │ HTTPS
┌───────────────────────▼─────────────────────────────────┐
│ 银联商务 → 微信 / 支付宝 / 云闪付 / 银行卡等支付渠道   │
└─────────────────────────────────────────────────────────┘
```

### 4.2 设计原则

- 业务系统只依赖内部支付服务，不直接散落银联商务字段。
- 银联商务协议封装在独立适配层，便于升级接口或增加其他支付服务商。
- 支付订单和业务订单分离，一笔业务订单可以对应多次支付尝试。
- 金额统一使用最小货币单位整数，例如人民币“分”。
- 支付成功必须由服务端确认，前端不能直接修改订单或履约状态。
- 所有外部通知和管理操作均可审计、可重放、可追踪。
- 状态变更应通过有限状态机执行，禁止任意覆盖状态。

## 五、核心数据模型

以下模型为逻辑模型，字段名可按项目技术栈调整。

### 5.1 业务订单 BusinessOrder

| 字段 | 说明 |
|------|------|
| id | 内部主键 |
| businessOrderNo | 业务订单号，唯一 |
| userId/customerId | 下单主体 |
| orderType | 商品、服务、充值、订阅等业务类型 |
| title/description | 业务摘要 |
| amountCents | 应付金额，整数分 |
| currency | 币种，默认 CNY |
| status | 待支付、已支付、已取消、已履约、已退款等 |
| snapshot | 商品、价格和业务规则快照 |
| expiresAt | 业务订单过期时间 |
| createdAt/updatedAt | 创建及更新时间 |

### 5.2 支付订单 PaymentOrder

| 字段 | 说明 |
|------|------|
| id | 内部主键 |
| paymentOrderNo | 系统支付订单号，唯一并提交给银联商务 |
| businessOrderId | 关联业务订单 |
| provider | 支付服务商，例如 CHINAUMS |
| channel | 微信、支付宝、云闪付等渠道 |
| scene | PC、H5、公众号、小程序、App 等场景 |
| amountCents | 本次支付金额 |
| currency | 币种 |
| status | CREATED、PENDING、SUCCESS、FAILED、CLOSED、REFUNDING、REFUNDED |
| providerOrderNo | 银联商务或目标渠道交易号 |
| requestId | 外部请求标识，用于排查 |
| payPayload | 支付地址、二维码内容或客户端唤起参数，按需保存且需脱敏 |
| failureCode/failureMessage | 失败原因 |
| paidAt/closedAt | 支付或关闭时间 |
| expiresAt | 支付订单过期时间 |
| createdAt/updatedAt | 创建及更新时间 |

### 5.3 支付通知 PaymentNotification

| 字段 | 说明 |
|------|------|
| id | 内部主键 |
| provider | 通知来源 |
| notificationId | 银联商务通知标识；没有时使用报文摘要 |
| paymentOrderNo | 关联支付订单号 |
| signatureValid | 验签结果 |
| rawPayload | 原始通知报文，敏感字段脱敏或加密保存 |
| normalizedPayload | 标准化后的通知内容 |
| processStatus | RECEIVED、PROCESSED、IGNORED、FAILED |
| errorMessage | 处理失败原因 |
| receivedAt/processedAt | 接收和完成时间 |

通知标识或报文摘要应建立唯一约束，作为通知层第一道幂等保障。

### 5.4 退款单 PaymentRefund

| 字段 | 说明 |
|------|------|
| refundOrderNo | 系统退款单号，每次退款尝试唯一 |
| paymentOrderId | 原支付订单 |
| amountCents | 退款金额 |
| reason | 退款原因 |
| status | CREATED、PROCESSING、SUCCESS、FAILED、CLOSED |
| providerRefundNo | 银联商务退款交易号 |
| operatorId | 发起退款的系统或管理员 |
| failureCode/failureMessage | 失败原因 |
| refundedAt | 退款完成时间 |
| createdAt/updatedAt | 创建及更新时间 |

银联商务接入指引明确说明：退款失败后可以重新发起，但新的退款尝试必须生成新的退款订单号。复用旧退款单号会得到旧交易结果。

### 5.5 对账差异 ReconciliationDifference

建议记录账单日期、支付订单、渠道金额、系统金额、差异类型、处理状态、处理人和处理说明，用于处理“渠道成功但系统未入账”等异常。

## 六、订单号与幂等设计

### 6.1 订单号规则

支付订单号和退款订单号应满足：

- 全局唯一
- 不包含用户隐私或业务敏感信息
- 在银联商务允许的长度和字符范围内
- 能区分环境，避免测试和生产冲突
- 不依赖数据库自增 ID 暴露业务规模

示例逻辑结构：

```text
环境标识 + 业务类型 + UTC 时间 + 随机序列
```

具体格式必须满足所选银联商务产品的字段长度限制。

### 6.2 下单幂等

前端创建订单时携带客户端幂等键，后端按“用户 + 业务对象 + 幂等键”控制重复提交。对同一幂等键：

- 已有可支付订单时返回原订单。
- 已支付时返回支付成功状态。
- 已关闭或已失败且允许重试时，新建支付订单，但不重复创建业务订单。

### 6.3 通知幂等

银联商务可能重复发送通知，也可能出现通知和主动查询并发。处理支付成功时必须在数据库事务中：

1. 锁定或条件更新支付订单。
2. 只有非成功状态可以首次转为成功。
3. 写入外部交易号和支付时间。
4. 更新业务订单。
5. 创建唯一履约记录或投递唯一履约事件。
6. 标记通知处理完成。

即使收到多次相同通知，也只能产生一次支付入账和一次业务履约。

## 七、支付主链路

### 7.1 创建订单

```text
用户选择商品和支付方式
  → 前端提交业务对象、渠道、支付场景和客户端幂等键
  → 后端读取商品及价格配置
  → 后端校验库存、销售状态、用户资格和金额
  → 创建业务订单和支付订单
  → 后端组装银联商务下单请求并进行平台认证
  → 银联商务返回支付地址、二维码内容或客户端支付参数
  → 后端返回安全的支付发起数据给前端
```

关键要求：

- 前端只能提交商品或方案标识，不能决定最终金额。
- 后端下单前重新读取价格，并将价格快照保存在业务订单中。
- 同一笔业务订单允许重新发起支付，但同一时间只保留一个有效支付尝试，或明确支付竞争处理规则。
- 通知地址由后端配置，不能信任前端传入。
- 商品描述不得包含密钥、内部备注或个人敏感信息。

### 7.2 调起支付

银联商务根据产品和场景可能返回：

- PC 收银台或 H5 跳转 URL
- 二维码字符串或二维码地址
- 微信公众号支付参数
- 微信小程序跳转参数
- App SDK 或 URL Scheme 参数

前端只负责按后端返回的类型执行展示或跳转。银联商务密钥、请求签名材料和商户私密参数不能下发到前端。

### 7.3 支付完成后的前端处理

用户从支付页面返回后，前端进入“支付结果确认中”页面：

1. 使用系统支付订单号查询业务后端。
2. 后端读取本地支付订单状态。
3. 状态仍为 PENDING 时，后端可按策略触发一次银联商务主动查询。
4. 前端短时间轮询，直到成功、失败、关闭或达到等待上限。
5. 超过等待上限时提示用户稍后在订单中心查看，不能直接判定失败。

前端返回、浏览器跳转、小程序 `onShow` 或客户端 SDK 回调都不是最终入账依据。

## 八、异步通知与签名验证

### 8.1 通知处理顺序

```text
接收原始 HTTP 通知
  → 解析 Content-Type 和字符编码
  → 保存通知接收记录
  → 验证签名
  → 校验商户号、订单号、金额、币种和交易状态
  → 幂等更新支付订单
  → 更新业务订单并触发履约
  → 按银联商务要求返回成功响应
```

任何一项校验失败都不能更新支付成功状态。

### 8.2 通知验签原则

根据接入指引附件，支付结果通知验签使用参数管理中的“通讯密钥”。基本规则为：

1. 对 HTTP 通知参数执行符合文档要求的 URL Decode。
2. 排除 `sign` 字段以及文档规定不参与签名的字段。
3. 按参数名称 ASCII 升序排列。
4. 按 `key=value` 形式拼接，字段之间使用 `&`。
5. 在拼接字符串末尾追加通讯密钥。
6. 使用文档指定算法计算摘要；附件示例使用 SHA256。
7. 统一签名大小写后，使用时间安全比较验证签名。

伪代码：

```text
signContent = sortAscii(params without sign)
  .map(key => key + "=" + decodedValue)
  .join("&")
  + communicationKey

expectedSign = SHA256(signContent)
valid = timingSafeEqual(expectedSign, receivedSign)
```

实际实现必须进一步确认：空字段是否参与、重复字段如何处理、空格与 `+` 的解码方式、字符编码、摘要输出大小写以及 Content-Type。

### 8.3 业务校验

验签成功不代表通知一定可直接入账，还必须校验：

- 商户号属于当前环境和当前系统。
- 支付订单号存在且未被其他订单使用。
- 通知金额等于支付订单金额。
- 币种一致。
- 外部交易状态属于明确的成功状态。
- 外部交易号未绑定到另一笔支付订单。
- 通知时间和订单状态不存在明显异常。

### 8.4 通知响应和重试

通知响应的状态码和响应正文严格按照银联商务产品文档返回。业务系统只有在本地事务成功提交后才能确认通知处理成功，否则应让银联商务继续重试。

对于持续失败的通知：

- 保留原始报文和错误原因。
- 进入告警和人工处理队列。
- 支持管理员在修复原因后安全重放。
- 重放仍经过相同验签、校验和幂等逻辑。

## 九、主动查询与订单关闭

### 9.1 主动查询触发条件

- 用户返回支付结果页但本地仍为 PENDING。
- 异步通知长时间未到达。
- 通知处理发生网络或数据库异常。
- 定时任务扫描到超时未决订单。
- 客服或管理员发起异常核查。

查询结果为成功时，复用异步通知相同的“确认支付成功”领域方法，不得另写一套不幂等的履约逻辑。

### 9.2 订单关闭

业务订单取消或支付超时后：

1. 检查本地订单仍可关闭。
2. 调用银联商务关闭接口。
3. 根据返回结果或后续查询更新状态。
4. 释放库存或其他业务占用资源。

关闭和支付成功可能并发。如果查询或通知确认支付已经成功，不能再将本地订单覆盖为关闭状态。

### 9.3 定时补偿

建议配置支付补偿任务：

- 短间隔扫描最近的 PENDING 订单并查询。
- 超过支付有效期的订单尝试关闭。
- 多次查询失败进入人工处理队列。
- 使用分布式锁或任务唯一键，避免多个实例重复执行。
- 设置查询频率上限，避免触发银联商务限流。

## 十、退款链路

### 10.1 退款前校验

- 原支付订单已经成功。
- 可退款余额大于等于本次退款金额。
- 多次退款累计金额不超过实付金额。
- 业务订单满足退款规则。
- 操作人具有退款权限。
- 高金额退款经过审批或二次确认。

### 10.2 退款流程

```text
用户申请或管理员审核退款
  → 业务系统创建唯一退款单
  → 调用银联商务退款接口
  → 记录受理结果
  → 接收退款通知或主动查询
  → 更新退款单和支付订单退款金额
  → 执行业务侧撤销、回收权益或退款后处理
```

“退款请求已受理”不等于退款成功。最终结果应以银联商务退款通知或退款查询为准。

### 10.3 退款失败和重试

- 网络超时后先查询原退款单，不要立即重复退款。
- 已确认失败且允许重新发起时，创建新的退款订单号。
- 不复用失败退款单号。
- 每次尝试都关联原退款申请，便于计算累计退款金额。
- 业务回收失败不能改变支付渠道已经退款的事实，应进入业务补偿队列。

## 十一、对账与资金核对

支付通知解决实时入账，对账解决长期正确性，两者不能互相替代。

### 11.1 每日对账

1. 按银联商务账单日期下载交易或结算账单。
2. 校验文件签名、摘要、完整性和账单日期。
3. 将账单行按商户订单号或外部交易号与系统支付订单匹配。
4. 比较交易状态、金额、退款金额和手续费。
5. 生成差异记录。
6. 所有差异均进入管理员待处理清单，对账任务不得自动修改订单或权益。
7. 管理员重新查询渠道并确认修复，无法安全修复的差异进入财务和技术联合处理流程。

### 11.2 常见差异

- 渠道成功、系统仍为待支付。
- 系统显示成功、渠道无交易。
- 金额或币种不一致。
- 渠道已退款、系统退款状态未完成。
- 重复交易或外部交易号冲突。
- 账单交易存在但系统订单不存在。

### 11.3 对账文件安全

- 原始账单加密保存并限制访问。
- 账单下载凭证与支付密钥分权管理。
- 账单不得通过普通日志或前端接口完整输出。
- 差异处理应记录处理人、时间、依据和最终结论。

## 十二、安全方案

### 12.1 密钥与配置

测试和生产参数必须完全隔离，至少包括：

- API Base URL
- 商户号和终端号
- 应用标识
- 请求认证密钥或证书
- 通知通讯密钥
- 通知地址和返回地址

密钥应保存在环境变量、密钥管理服务或受控配置中心中，不得：

- 提交到 Git
- 写入前端代码
- 返回给浏览器
- 输出到普通日志
- 直接保存在可公开下载的配置文件中

密钥需要支持版本化、轮换和紧急吊销。

### 12.2 接口安全

- 所有支付接口使用 HTTPS。
- 创建订单和查询用户订单需要认证和权限校验。
- 通知接口无需登录，但必须验签和校验业务字段。
- 退款和人工补单接口仅限授权管理员。
- 创建订单、查询和退款接口分别设置限流。
- 防止用户横向查询他人的订单。
- 严格校验所有枚举、金额、订单号和 URL 参数。
- 不允许前端传入任意通知地址或支付金额。

### 12.3 日志脱敏

日志可以记录内部订单号、请求 ID、接口名称、状态码和耗时，但应脱敏：

- 通讯密钥、证书和签名原文
- 用户姓名、手机号、邮箱和渠道用户标识
- 银行卡号、证件号和付款账户
- 完整支付参数、支付 URL 和二维码内容

### 12.4 风险控制

- 同一用户、设备和 IP 的下单频率限制。
- 异常金额、异常退款比例和高频失败告警。
- 管理后台退款二次确认和操作审计。
- 支付成功但履约失败的实时告警。
- 外部交易号唯一性检查。
- 生产密钥访问和配置变更审计。

## 十三、项目接入方式

### 13.1 后端模块划分

建议在业务系统中建立以下模块：

```text
payment/
├── controller          # 对前端和通知暴露 HTTP API
├── application         # 创建订单、确认支付、退款等用例
├── domain              # 支付订单、状态机、幂等和领域事件
├── repository          # 数据库持久化
├── providers/
│   └── chinaums        # 银联商务认证、接口和报文转换
├── notification        # 通知解析、验签、处理和响应
├── reconciliation      # 账单下载及对账
└── jobs                # 查询、关闭、退款和履约补偿任务
```

银联商务适配层向业务系统暴露统一接口，例如：

```ts
interface PaymentProvider {
  createPayment(input: CreatePaymentInput): Promise<CreatePaymentResult>
  queryPayment(input: QueryPaymentInput): Promise<PaymentResult>
  closePayment(input: ClosePaymentInput): Promise<ClosePaymentResult>
  createRefund(input: CreateRefundInput): Promise<CreateRefundResult>
  queryRefund(input: QueryRefundInput): Promise<RefundResult>
  verifyNotification(input: RawNotification): VerifiedNotification
}
```

### 13.2 通用内部 API

```text
GET  /api/payment/methods
POST /api/payment/business-orders
POST /api/payment/orders
GET  /api/payment/orders/:paymentOrderNo
POST /api/payment/orders/:paymentOrderNo/close
POST /api/payment/notifications/chinaums
POST /api/payment/orders/:paymentOrderNo/refunds
GET  /api/payment/refunds/:refundOrderNo
GET  /api/payment/my-orders

GET  /api/admin/payment/orders
GET  /api/admin/payment/refunds
POST /api/admin/payment/refunds
POST /api/admin/payment/reconcile
```

接口路径可按项目约定调整，但异步通知应使用独立路径，避免被普通登录中间件拦截。

### 13.3 前端接入

前端需要实现：

- 支付方式选择
- 创建订单的防重复提交
- 二维码、跳转或客户端唤起
- 支付结果确认页
- 短时间订单状态轮询
- 支付超时、取消和处理中提示
- 订单及退款记录
- 从支付结果页返回业务页面的安全跳转

前端不实现签名、不保存密钥、不直接调用银联商务需要私密认证的接口。

### 13.4 业务履约集成

支付模块确认成功后发布内部事件：

```text
PaymentSucceeded
PaymentClosed
RefundSucceeded
```

具体业务监听事件完成发货、开通服务、增加余额或更新订阅。履约记录使用支付订单号作为唯一键，确保重复事件不会重复履约。

如果履约失败：

- 支付订单仍保持 SUCCESS。
- 履约记录标记失败并进入重试队列。
- 超过重试次数后告警和人工处理。
- 不得因为业务失败将已成功支付直接改成失败。

## 十九、当前代码落地与配置清单

### 19.1 已实现链路

当前系统采用银联商务 C扫B 一次性聚合二维码，已经实现：

```text
前端选择套餐
  → 后端按支付策略计算金额并生成银商规范 billNo
  → 调用 /v1/netpay/bills/get-qrcode
  → 前端展示 billQRCode 并轮询
  → 银联商务通知 /api/payment/notifications/chinaums（兼容 billNo / merOrderId）
  → 通知验签后主动调用 /v1/netpay/bills/query 复核
  → 金额、商户号、订单状态校验
  → 事务内将 PaymentOrder 置为 paid
  → 按银联 targetSys 回写用户实际使用的支付钱包
  → 创建或延长 UserMembership，并更新用户会员状态
```

同时提供未支付订单主动查询与二维码关闭；通知采用唯一通知号、订单条件更新和事务履约三层幂等。前端只展示支付结果，不能直接把订单改为成功。

API 进程启动后还会运行支付生命周期 Worker：定期补偿查询未支付订单和处理中退款、关闭已过期二维码、将到期会员改为 `expired`，并在用户不再拥有其他有效会员时同步旧版付款状态。每轮任务先竞争 `BackgroundJobLease` 数据库租约，因此多实例部署不会并发执行同一轮任务；支付与关单并发时先查询银联状态，以支付成功为优先结果。各处理阶段使用独立错误边界，首轮数据库或租约异常不会取消后续定时轮询；关单失败的记录会移到下一轮队尾，避免固定异常订单长期占满批次。

每天到达配置小时后，Worker 对前一个完整中国自然日执行逐单交易状态核对。核对范围包括当日创建、支付或退款的本地订单；定时执行和管理员发起的立即执行都只查询并记录差异，不自动修改订单、退款或会员状态。所有异常必须由管理员在全站支付运营台显式选择“复核并修复”或在完成线下核查后记录处理说明。复核修复只接受银联可验证且金额一致的支付成功、订单关闭和退款成功结果，不提供“强制置为已支付”。该能力不是清算账单的全量双向勾兑，财务仍需登录银联商务商户平台复核“公共支付”清算明细或汇总。

当前代码中的接口为：

| 接口 | 用途 |
|------|------|
| `GET /api/payment/config` | 读取价格与通道是否就绪 |
| `POST /api/payment/orders` | 创建本地订单并换取银联商务二维码 |
| `POST /api/payment/orders/:orderNo/query` | 主动查询并同步支付结果 |
| `POST /api/payment/orders/:orderNo/close` | 关闭未支付二维码 |
| `POST /api/payment/notifications/chinaums` | 接收银联商务 form 通知，返回 `SUCCESS` / `FAILED` |
| `GET /api/admin/payment-orders` | 管理员分页查看全站支付订单 |
| `GET /api/admin/payment-orders/:orderNo` | 查看订单、脱敏通知、退款、权益快照、对账和管理员操作时间线 |
| `POST /api/admin/payment-orders/:orderNo/refunds` | 管理员发起全额退款并在成功后回收权益 |
| `POST /api/admin/payment-refunds/:refundOrderNo/query` | 主动查询退款并同步最终结果 |
| `GET /api/admin/payment-reconciliation/overview` | 读取最近对账批次和全站异常计数 |
| `GET /api/admin/payment-reconciliation/items` | 分页读取待处理或历史对账明细 |
| `POST /api/admin/payment-reconciliation/runs` | 管理员手动执行指定业务日对账 |
| `POST /api/admin/payment-reconciliation/items/:id/recheck` | 管理员显式确认后重新查询渠道并执行安全修复 |
| `POST /api/admin/payment-reconciliation/items/:id/resolve` | 记录线下核查说明并关闭异常 |

当前已补齐管理员全额退款、退款查询、支付/退款补偿查询、自动过期关单、会员到期处理、本地订单逐笔日终核对，以及支付成功后按银联 `targetSys` 回写实际钱包渠道。部分退款、用户自助退款，以及依赖渠道全量账单的“渠道有、本地无”识别仍按本文第十至十一章作为后续生产保障能力。

全站支付订单支持打开审计详情，按时间倒序聚合订单创建、二维码生成、支付/关单、脱敏异步通知、退款、对账和管理员操作。现有 `UserMembership` 未保存来源支付订单，因此详情中的会员信息明确标记为按用户与考试类型关联的当前权益快照，不作为单笔订单的精确权益归因凭证；后续若需要不可变的逐次权益流水，应新增订单级权益变更记录。

| `CHINAUMS_TID` | 是 | 银联商务终端号，8 位 |
| `CHINAUMS_INST_MID` | 是 | 当前 C扫B 业务固定使用 `QRPAYDEFAULT`，除非银商另行指定 |
| `CHINAUMS_MSG_SRC_ID` | 是 | 取生产参数中的 4 位“系统编号”，支付账单号必须以它开头；不要误用“接入来源”域名 |
| `CHINAUMS_COMMUNICATION_KEY` | 通知联调/生产必填 | 银商分配的通讯密钥，只用于异步通知 SHA256/MD5 验签；仅测试出站接口时可暂不配置 |
| `CHINAUMS_NOTIFY_URL` | 通知联调/生产必填 | 银商服务器可公网 POST 的完整通知地址；仅测试下单、查询和关单时可暂不配置 |

可选参数：

| 环境变量 | 默认值 | 说明 |
|---------|--------|------|
| `CHINAUMS_RETURN_URL` | 空 | 浏览器体验回跳地址；不是支付成功依据 |
| `CHINAUMS_ORDER_DESCRIPTION` | `AceMock 在线会员订阅` | 账单描述，不超过 128 字符 |
| `CHINAUMS_TIMEOUT_MS` | `10000` | 调用银商接口的超时毫秒数 |
| `CHINAUMS_ORDER_EXPIRE_MINUTES` | `15` | 一次性二维码有效分钟数 |
| `PAYMENT_PURCHASE_ALLOWED_EMAILS` | 空 | 正式支付验证期可填写逗号分隔的登录邮箱白名单；非空时只有白名单账号可以创建真实订单，完成验证后清空即恢复全部登录用户购买 |
| `PAYMENT_LIFECYCLE_ENABLED` | 本地 `false`，测试/生产 `true` | 是否启动支付生命周期 Worker；生产环境开启银联商务时必须为 `true`，否则运行时校验和 API 启动都会失败 |
| `PAYMENT_LIFECYCLE_POLL_INTERVAL_MS` | `60000` | Worker 轮询间隔，最小 10 秒 |
| `PAYMENT_LIFECYCLE_LEASE_MS` | `300000` | 跨进程数据库租约时长，不能短于轮询间隔 |
| `PAYMENT_LIFECYCLE_BATCH_SIZE` | `20` | 每类状态每轮最多处理的记录数 |
| `PAYMENT_PENDING_QUERY_AGE_SECONDS` | `30` | 待支付订单创建/上次查询后至少等待多久再补偿查询 |
| `PAYMENT_REFUND_QUERY_AGE_SECONDS` | `30` | 退款记录上次更新后至少等待多久再补偿查询 |
| `PAYMENT_RECONCILIATION_ENABLED` | 本地 `false`，测试/生产 `true` | 是否启用每日交易对账 |
| `PAYMENT_RECONCILIATION_HOUR` | `2` | 每天在中国时区几点后核对前一自然日，取值 0–23 |
| `PAYMENT_RECONCILIATION_BATCH_SIZE` | `100` | 对账时每批读取的本地订单数量 |

API_RUNTIME_ENV=test

如 API 未通过 80 端口反向代理，需要在通知地址中明确写可公网访问的端口。防火墙、安全组和反向代理必须允许银联商务访问通知路径；该路径不能跳转登录、不能要求 Cookie，也不能被前端 history fallback 改写为 HTML。

### 19.4 正式域名 + HTTPS 切换

正式上线只替换部署配置，不修改支付业务代码：

```dotenv
API_RUNTIME_ENV=prod
CHINAUMS_ENABLED=true
CHINAUMS_ENV=prod
CHINAUMS_BASE_URL=https://api-mop.chinaums.com
CHINAUMS_MID=<15位正式商户号>
CHINAUMS_EXPECTED_MID=<经审批的同一15位正式商户号>
CHINAUMS_NOTIFY_URL=https://<正式域名>/api/payment/notifications/chinaums
CHINAUMS_RETURN_URL=https://<正式域名>/
PAYMENT_PURCHASE_ALLOWED_EMAILS=<正式验证账号邮箱>
```

生产启动时会强制检查 `CHINAUMS_ENV=prod`、生产 API 地址、正式商户号一致性、通讯密钥和公网 HTTPS 通知地址；返回地址如有配置也必须使用 HTTPS。测试密钥和生产密钥应分开保管，不允许复用。部署前应依次运行 `npm run verify:chinaums-signature`、`npm run verify:chinaums-notification`、`npm run validate:chinaums:prod` 和 `npm run validate:runtime`。

### 19.5 本项目正式商户上线清单

| 项目 | 正式值或要求 |
|------|--------------|
| 商户主体 | 上海解航云舟科技有限公司 |
| 商户号 | 由生产私有配置提供，并须与天满已上线的当前主商户号一致；禁止在仓库文档或示例配置中保存真实编号 |
| 支付产品 | C扫B 聚合二维码；天满上线产品和商户签约范围必须包含实际开放的钱包 |
| 生产参数 | 从“参数管理 → 我的生产参数”取得同一参数组的 appId、appKey、终端号、接入来源、系统编号和通讯密钥，禁止混用测试参数；系统编号映射 `CHINAUMS_MSG_SRC_ID`，接入来源属于平台登记信息，不作为当前 C扫B 请求字段擅自上送 |
| 上线申请 | “我是开发者 → 支付接口上线 → 支付服务上线”；绑定已有商户后提交所需产品，IP 字段不填写 |
| 通知地址 | 正式域名下的 `https://<域名>/api/payment/notifications/chinaums`，公网直接可访问且不能跳转登录 |

仅有商户号不足以发起正式交易。取得上述整组生产参数并完成天满支付服务上线审批后，才能在服务器私有 `.env` 中启用 `CHINAUMS_ENABLED=true`；任何 appKey 或通讯密钥都不得写入本文件或提交 Git。

### 19.6 财务清算对账

《新网服教程-商户对账》描述的是银联商务商户统一服务平台中的人工账务核对，不是当前天满 C扫B API 的自动全量账单接口。财务人员登录 `https://service.chinaums.com/uisportal/` 后，进入“账务中心 → 对账查询 → 明细查询”，按清算时间查询；聚合钱包交易的应用类型选择“公共支付”，可查看明细或汇总并下载 XLS、XLSX、CSV。系统后台的“立即对账”只核对本地已有订单，二者应共同用于上线后的日常复核。
