# 4.8 诊断测试

本文档用于定义“诊断测试”功能的产品边界、页面行为、核心流程、异常容错与后续边界。强调可用于测试验收的逻辑标准与数据来源，不做具体界面实现细节。

---

## 功能边界与目的

### 1.1 目标

诊断测试面向学生用户（会员与非会员），在指定考试类型下提供一条完整的测评链路：筛选可测试卷 → 开始/继续作答 → 交卷 → 分析 → 查看报告。

### 1.2 范围

本功能定义：

- 诊断列表的可见规则与状态展示
- 试卷开始、答题中恢复、提交、返回、交互
- 权益配额判定和消耗规则
- 分析中间态与结果页入口
- 异常分支与边界场景

不包括：

- 试卷上传器的文件解析细节
- 试卷/题目编辑与审核流程
- 诊断算法模型训练与重建模

### 1.3 术语与数据模型（诊断域）

- `examType`：考试类型，例如 `ESAT / TMUA / STEP`。
- `paperType`：试卷来源分类
  - `realPaper`：真题卷（诊断测试入口来源）
  - `mockPaper`：模考卷（不进入诊断测试列表）
  - `aiPaper`：AI 生成卷（不进入诊断测试列表）
- `paper` 状态：`published / online` 为可用状态，其他状态不可进入诊断列表。
- `attempt`：一次独立诊断作答，对应一条 `ExamRecord`。重新测试必须创建新的 attempt，不覆盖历史已完成记录。
- `testStatus`：诊断列表根据当前用户、当前试卷最近一次 attempt 派生出的展示状态，取值为 `not_started / in_progress / completed`。
- `activeDiagnosticKey`：进行中诊断的服务端唯一占用标识，按“用户 + 考试类型”约束；交卷完成后释放。
- 重测资格不单独持久化，而是在用户点击时根据最近一次状态、剩余额度、考试类型权限及进行中诊断冲突实时判定。

### 1.4 角色与权限边界

| 角色 | 能做的事 | 限制 |
| --- | --- | --- |
| 学生 | 查看诊断列表、开始/继续测试、交卷、查看报告 | 受会员权益与配额限制 |
| 会员用户 | 在试卷可见范围内可获得更多可测次数 | 仍受考试类型权限与试卷状态限制 |
| 管理员（后台） | 仅管理员后台操作，不作为前台诊断核心角色 | 如需测试，需临时账号行为可追溯 |

### 1.5 试卷进入诊断列表的硬约束

诊断列表中只展示满足以下条件的试卷：

1. `paperType = realPaper`
2. 试卷状态为已发布/已上线
3. 考试类型在系统支持范围内（ESAT / TMUA / STEP）
4. 当前用户有该考试类型的访问权限

## 页面描述

### 2.1 入口与布局

- 入口路径：`/assessment`
- 页面主干目标：展示当前可测试卷、状态与操作入口
- 列表数据字段：考试类型、试卷名称、状态、配额信息、操作按钮

### 2.2 列表状态计算方式

列表状态不是试卷静态字段，而是按当前用户在该试卷下最近创建的一次 `ExamRecord` 派生：

- 无考试记录：显示“未开始”
- 最近一次记录为 `in_progress`：显示“进行中”；即使存在更早的完成记录，也优先呈现最新 attempt 的进行中状态
- 最近一次记录为 `submitted`：显示“已完成”
- 历史完成记录必须保留；重新测试创建新记录后，列表状态随新记录切换，不修改旧记录

### 2.3 按钮与配额展示规则

- 未开始：显示“开始测试”
- 进行中：显示“继续测试”
- 已完成：显示“查看报告”和“重新测试”
- “重新测试”按钮可见仅表示已有一条完成记录，不等于已通过本次重测资格校验
- 点击“开始测试”或“重新测试”后统一执行考试类型权限、诊断额度和进行中诊断冲突校验；不满足条件时不创建新 attempt，并给出对应提示
- 继续测试不重复扣配额；正式提交后按考试完成维度扣减
- 客户端只发起正常开始请求，是否允许创建新 attempt 完全以后端本次校验结果为准

### 2.4 报告页入口与导航

- 已完成测试可直接进入对应报告页
- 报告页展示该次测试结果，不展示其他试卷数据
- 在报告页应支持：
  - 回看题目解析
  - 跳转学习入口（题目库/推荐路径）
- 诊断列表中的“查看报告”和“重新测试”是两个独立动作；报告生成中不改变重测入口的业务含义，但重测仍必须通过正式资格校验

## 核心流程

### 3.1 诊断试卷入列链路

从试卷管理到诊断列表的链路固定如下：

1. 在真题库完成上传/入库
2. `paperType` 设为 `realPaper`
3. 试卷状态设为上线/发布
4. 诊断列表查询基于已发布真题卷进行筛选

若为 `mockPaper` 或 `aiPaper`，即使已上传，也不出现在该列表。

### 3.2 开始与恢复流程

- 点击“开始测试”时，创建该用户该试卷的进行中进度记录并进入答题。
- 点击“继续测试”时，恢复最近一次进行中记录（包含题号、答案、计时偏移）。
- 从答题页返回列表时，列表应切换为“继续测试”。

### 3.3 中断恢复与结果保护

- 切换标签、刷新或离开时，已作答数据和时间应持久化；
- 仅在用户主动提交后才生成最终报告；
- 中途离开不应直接进入完成态，不应提前扣除完成类配额。

### 3.4 重新测试流程

重新测试是正式业务流程，不是调试入口。流程固定如下：

1. 前置条件：当前试卷最近一次 attempt 为 `submitted`，诊断列表显示“重新测试”。
2. 用户点击后，前端先检查当前考试类型是否开放，并查询该考试类型的诊断权益。
3. 系统检查当前用户在同一 `examType` 下是否存在其他 `in_progress` 的真题诊断：
   - 不存在：允许继续创建流程。
   - 存在且属于其他试卷：阻止重测，提示用户先完成正在进行的诊断。
   - 存在且属于当前试卷：不得创建第二条记录，应恢复已有记录。
4. 权益不足时不创建新 attempt，保留历史报告和完成记录，提示用户补充权益。
5. 校验通过后创建全新的 `ExamRecord`，新记录从第一题或第一个模块开始；不得复制上一轮答案、题目状态、计时或提交标识。
6. 新 attempt 创建后，该试卷列表状态切换为“进行中”，主操作变为“继续测试”。
7. 新 attempt 提交后独立生成成绩与报告；历史 `ExamRecord`、历史答案及对应报告任务结果继续保留，试卷的默认报告入口更新为最近一次成功生成的报告。

重新测试的客户端请求只标识目标试卷。用户身份来自登录上下文，考试类型与试卷状态从服务端 `Paper` 数据读取；最终资格以后端状态、权益与并发校验结果为准。

### 3.5 答题页初始化与提交前校验

- 按试卷顺序加载题目，建立进度索引；
- 支持上一题/下一题，允许按题号跳转；
- 答题切换不得丢失历史作答；
- 提交前校验：
  - 用户确认交卷
  - 作答数据合法
  - 正常存储结束时间与最终答案

### 3.6 在线答题过程（参考 4.6）

- 计时：
  - 诊断测试采用倒计时（试卷时长分钟 × 60 秒）；
  - 练习场景采用正计时；
  - 剩余 5 分钟进入预警态；
  - 切页/锁屏暂停计时，恢复时需确认继续。
- 作答与选项：
  - 题目卡状态按 未答 / 已答 / 跳过 / 当前 维护；
  - 单选题单点互斥、可取消；多选按题目定义保存。
- 耗时：
  - 记录每道题停留时长，可用于后续分析；用户不需手工提交。
- 交互约束：
  - 提前交卷需确认；若有未答题，提示未答计入未答；
  - 返回非诊断类练习通常仅退出，不自动提交；
  - 诊断返回入口执行“中断不放弃”恢复逻辑。

### 3.7 交卷与分析中间态

- 交卷成功后进入分析中状态，不允许继续改答案；
- 预计时长：10 秒（前端模拟）；
- 进度条 0%→100%，同步题号/剩余时间文案；
- 到达 100% 自动跳转到报告完成页。

### 3.8 权益与配额逻辑

- 配额来源于会员权益（按考试类型）；
- 开始或重新测试前执行一次额度预检查，但创建进行中记录本身不计为已使用次数；
- 正式交卷时在数据库事务内再次校验额度，交卷成功形成 `submitted` 记录后计为一次有效使用；
- “继续测试”仅恢复，不重复消耗；
- 免费用户已用完该考试类型诊断次数时不能重新测试；拥有有效不限次权益的会员或管理员可继续重测；
- 配额不足时，不得提交为完成态，也不得覆盖已有报告，应提示权益不足并引导权益补充；
- 重复交卷必须保持幂等，同一 attempt 只能计入一次诊断用量。

### 3.9 数据流与关键状态

- 数据链：真题上线 → 列表可见 → 开始/恢复 → 进度更新 → 提交 → 分析中 → 报告展示
- 状态演化：
  - 试卷：上线控制
  - 用户考试：未开始 → 进行中 → 已完成
  - 重新测试：已完成 → 新建 attempt → 进行中 → 已完成
  - 进度：新建/更新/完成固化
  - 分析：待分析 → 分析中 → 成功/失败
- 并发约束：同一用户、同一 `examType` 同一时间只能存在一个进行中的真题诊断；该约束由 `activeDiagnosticKey` 在服务端和数据库共同保证。
- 交卷成功后必须清空该 attempt 的 `activeDiagnosticKey`，使后续重新测试具备创建新记录的条件。

### 3.10 验收参考点

- `realPaper` 上线后应在诊断列表可见；`mockPaper`/`aiPaper` 不可见；
- 列表状态与按钮文案与后端记录一致；
- 切页/刷新后可恢复进度；
- 交卷触发 10 秒分析中态并成功跳报告；
- 配额不足场景被阻断；
- 提交后报告与本次作答数据一致；
- 已完成试卷显示“重新测试”，点击后必须经过正常权益校验，不得携带调试绕过参数；
- 额度充足时重测创建新的 `ExamRecord`，旧答案、旧成绩和旧报告保持不变；
- 额度不足时重测不创建记录，页面提示额度不足；
- 同考试类型已有其他进行中诊断时，重测返回冲突提示且不创建第二条进行中记录；
- 新重测记录创建后列表显示“进行中”，完成后再次显示“已完成”。

## 异常容错

### 4.1 列表与状态异常

- 不满足可见条件的试卷不应展示；
- 并发开始或重测请求只能有一个成功创建进行中记录，其他请求返回“已有进行中诊断”；
- 试卷内容不完整时不允许进入。

### 4.2 在线答题异常

- 脱网时禁止提交，提示重试，历史进度尽量保留；
- 切页/锁屏应暂停计时并在返回时恢复；
- 页面刷新恢复后应保持进行中态，而不是回到未开始；
- 计时归零时需统一提示并触发自动提交。

### 4.3 重新测试异常

- 用户连续点击“重新测试”时，前端在请求期间禁用当前操作按钮；后端仍必须通过唯一占用约束防止重复创建；
- 同考试类型已有其他试卷进行中时，返回 `DIAGNOSTIC_IN_PROGRESS`，不得自动结束、覆盖或删除原诊断；
- 权益预检查通过但交卷时额度已被其他请求消耗时，以交卷事务内的最终校验为准；校验失败不得形成第二次有效用量；
- 新 attempt 创建失败时，原完成记录和历史报告保持可访问，列表刷新后应恢复服务端真实状态；
- 请求中的额外客户端字段不参与重测资格判定，服务端始终执行同一套状态、权益与并发校验。

### 4.4 分析与结果异常

- 分析超时后可提示失败并允许重试；
- 数据缺失时不展示伪造分数，生成可排查日志与时间戳；
- 报告加载异常时提供返回诊断列表或重试通道。

## 后续与非目标说明

### 5.1 非目标

- 不要求本版本重构接口命名；
- 分析过程当前可为前端模拟；接入真实分析服务时，保持状态模型即可平滑切换。

### 5.2 业务约定与后续校准

- “重新测试”是正式生产能力，必须复用正常开始、权益校验、并发占用和交卷流程；
- 当前重测资格采用实时派生规则；若未来需要按试卷、活动或用户单独关闭重测，应新增服务端策略字段与明确的管理入口，不得由前端自行推断；
- 管理与上架动作变更后应同步验证诊断列表入列与权限映射；
- 如遇“考试类型/用户权限/权益”定义变更，优先更新本节规则而非直接改动埋点逻辑。
