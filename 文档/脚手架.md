# 脚手架：首版实现与后续方向

## 当前首版（2026-09-12）

首版采用 **Skill 入口 + 固定工程模板 + 生成脚本**，重心是快速构建可修改、可运行的原型。源文件为 [prototype-builder](../skills/prototype-builder/SKILL.md)，通用约定和实际用法以该 Skill 及其引用文件为准。

- 输入：自然语言需求或已有规格、新项目目录；也支持在已有项目中继续修改。
- 开始业务代码前：形成精简的 `docs/project-spec.md`，明确页面、字段、操作、演示数据与本次范围，供并行任务共同使用。
- 输出：独立的 Vue 3 + TypeScript + Element Plus + Vite 前端、HTTP Mock 服务、共享接口类型、主题与分页组件、模块归属、启动与修改说明。
- Mock：不依赖数据库，支持增删改查、分页、搜索、空态/错误态和恢复示例；修改在本项目 `.local/` 保存，重启保留。
- 修改：按现有规格、模块和技术栈增量开发，不用生成器覆盖已有项目。普通脚本负责固定工程结构，Agent 根据规格实现具体业务。
- 首版范围暂不包括自动化治理与测试基线、存量项目全面规范改造、正式后端及生产部署；这些不作为生成原型的前置条件。

## 早期完整设想（保留作后续参考）

以下是早期较完整的方向，包含尚未纳入首版的企业交付能力，不代表当前全部实现。

我建议把它定位为一套 **“支持原型开发和存量改造的项目交付脚手架”**：把 QuizTest 中已经验证过的工程经验，提炼成规范、基础代码、开发工具和交付流程。

核心设计是：**新项目可以快速生成，已有项目可以逐步接入；Mock 与真实后端遵守同一套接口约定。**

我看了现有架构、开发规范、样式和部署流程。QuizTest 已经具备很好的提炼基础，例如统一请求层、分页交互、样式令牌、数据库迁移、环境校验。抽取时需要统一规范来源：此前 JSON 字段序列化规则的文档冲突已修正，当前以 [开发规范](1-开发规范.md) 第 2.2.1 至 2.2.4 节及 [AGENTS.md](../AGENTS.md) 为准。

下面是我建议的整体方案。

**先把脚手架分成五个部分，每个部分都有明确产物。**

| 部分 | 主要内容 | 交付形态 |
|---|---|---|
| 通用规范 | 架构分层、接口、分页、样式、模块边界、数据库、验收要求 | 版本化规范文档 |
| 标准工程 | 前端、后端、公共组件、请求封装、配置、日志 | 可运行项目模板 |
| 开发工具 | 初始化、生成模块、启动 Mock、检查项目、辅助改造 | 统一命令 |
| AI 工作流程 | 理解需求、定位模块、开发、检查、部署 | Skills 和项目规则入口 |
| 交付机制 | 构建、配置校验、迁移、发布、验证、回退 | 脚本、流水线和交付记录 |

这些内容要互相对应。例如，“所有分页统一”应该同时对应分页规范、分页组件、列表逻辑封装、生成模板和检查规则。

**技术架构首版继续沿用 QuizTest 的技术栈。**

前端采用 Vue 3、TypeScript、Element Plus；后端采用 Express、TypeScript、Prisma、MySQL。前后端独立运行、构建和部署，源码可以放在同一个仓库。

建议形成三类可复用内容：

| 类型 | 内容示例 | 使用方式 |
|---|---|---|
| 最小基础 | 应用布局、路由、请求、错误处理、分页、主题、环境配置 | 默认具备 |
| 可选能力 | 登录与权限、文件上传、操作审计、通知、后台管理 | 按项目启用 |
| 业务模块 | Quiz 的题库、考试、诊断、会员、支付规则 | 独立维护，按需接入 |

已有项目如果采用 React、Java 等技术，也可以先接入接口、模块治理和交付规范；技术栈迁移应单独评估。

**原型与真实开发，使用同一套页面和 API 调用。**

推荐保留这条调用链：

`页面 → 业务 API 模块 → 统一请求层 → Mock 或真实 API`

页面始终调用业务 API，演示数据集中在 Mock 层维护。这样切换后端时，页面的调用方式可以保持稳定。

Mock 可以采用 MSW，它支持在网络层拦截请求，也能将模拟逻辑复用于开发、测试和演示。[MSW 官方文档](https://mswjs.io/docs/)

建议提供三种运行方式：

| 模式 | 启动内容 | 主要用途 |
|---|---|---|
| 原型演示 | 前端 + Mock | 产品经理快速搭建、评审、修改交互 |
| 本地开发 | 前端 + API + 数据库 | 实现真实业务、调试数据 |
| 环境联调 | 本地前端 + 指定测试 API | 联调、验收、问题复现 |

Mock 要能支撑完整的操作过程。例如“新增客户”后，列表应出现该客户，总数应增加，详情页能够打开，刷新后是否保留也有明确约定。

建议默认包含：

- 正常、空数据、加载中、请求失败、无权限等场景。
- 搜索、筛选、排序、分页和新增编辑后的状态变化。
- 固定的初始数据和“一键恢复演示数据”。
- 演示身份切换，例如管理员与普通用户。

浏览器 Mock 适合独立演示；多人需要共享同一份演示数据时，再提供独立 Mock 服务。正式发布配置应校验 Mock 未启用，真实请求失败也不能自动切回假数据。

**接口契约应成为前后端和 Mock 的共同依据。**

建议用 OpenAPI 管理接口契约，统一描述请求、响应和错误，并接入类型生成与契约验证。OpenAPI 本身与具体编程语言无关，也便于存量项目接入。[OpenAPI 官方说明](https://www.openapis.org/what-is-openapi)

可以沿用 QuizTest 已有约定：

- 普通响应统一为 `success / code / errMsg / data`。
- 分页参数统一为 `page / pageSize`，结果统一为 `list / pagination`。
- 明确 HTTP 状态码与业务错误码的对应关系。
- 统一时间、金额、空值、排序、文件下载等边界规则。
- 后端请求与响应、Mock 数据都接受契约校验。

分页尤其值得继续提炼。现有“草稿筛选条件”和“已应用筛选条件”的区分很实用，可以封装成 `usePagedList`，连同搜索回到第一页、删除末页最后一项后的回退、请求竞态处理一起复用。

契约负责数据格式；权限规则、状态转换和业务计算仍需要相应实现和验收。

**前端统一标准要落实到主题、组件和页面模板。**

建议建立三层：

| 层次 | 统一内容 |
|---|---|
| 设计令牌 | 颜色、字号、间距、圆角、阴影、层级、布局宽度 |
| 标准组件 | 分页、表格、表单、弹窗、状态标签、加载与空状态 |
| 页面模板 | 列表页、详情页、编辑页、工作台、登录页 |

QuizTest 当前的黑白灰风格可以成为默认主题，品牌色、密度和布局则允许项目配置。

统一标准还要覆盖交互：表单校验出现的位置、按钮提交中的状态、错误是否重复提示、筛选条件是否保留、键盘操作和移动端适配策略。

对产品经理而言，最直接的价值是：选择一个“管理列表”模板，就已经获得一致的布局、搜索、分页、操作入口和异常状态。

**模块归属建议做成一份可检查的模块清单。**

每个模块都登记以下内容：

| 登记项 | 要回答的问题 |
|---|---|
| 业务职责 | 这个模块负责什么，边界在哪里？ |
| 代码位置 | 对应哪些页面、API、后端服务？ |
| 数据归属 | 哪些数据由它维护，谁有权修改？ |
| 公开能力 | 其他模块可以调用哪些接口？ |
| 依赖关系 | 它依赖哪些模块和外部服务？ |
| 权限与验收 | 谁能操作，怎样判断功能完成？ |
| 维护归属 | 由哪个人或角色负责？ |

例如，订单模块负责订单状态，会员模块负责权益生效；订单模块通过会员模块公开的能力发放权益。这样的边界可以同时指导开发人员和 AI 修改代码。

新项目可以按业务模块组织目录。旧项目先建立文件与模块的映射，也能开始治理，无需先完成全部目录调整。

**部署 Skill 建议拆成“流程、脚本、配置”三层。**

现有 QuizTest 部署流程中的版本确认、备份、迁移、运行时校验、健康检查都值得保留，但需要参数化。

- **Skill**：理解部署目标，确定环境、范围和版本，调用标准流程，解释结果。
- **脚本**：执行构建、产物校验、备份、迁移、发布和验证，返回明确结果。
- **项目配置**：提供应用名称、服务器、路径、启动方式、健康接口和密钥引用。

首版可以支持现有 Nginx、PM2、MySQL 部署方式。SMTP、支付渠道等依赖应随模块启用，避免普通原型也必须配置邮件和支付。

交付流程要分别定义应用版本回退和数据库恢复；数据库迁移是否兼容上一版应用，需要在发布前检查。

**存量项目改造，建议提供独立的接入流程。**

1. **建立现状基线。** 盘点启动方式、页面、接口、数据和部署流程，保留关键业务的运行证据。
2. **输出差距清单。** 区分运行阻塞、接口问题、权限问题、交互不一致和维护问题，并排出优先级。
3. **接入公共基础。** 逐步统一请求、错误、分页、样式和检查命令；旧接口通过适配层兼容。
4. **改造一个完整模块。** 从页面到数据库、从 Mock 到真实部署，完整跑通一条用户流程。
5. **按模块推广。** 新代码执行新规则，历史问题按计划消化；例外要记录原因、责任人和退出条件。

这种改造还需要版本机制：每个项目记录所用规范和脚手架版本，升级时生成差异和迁移建议，保护已有业务代码。

“企业级、可交付”也需要明确验收条件：

| 阶段 | 最低验收要求 |
|---|---|
| 原型可演示 | 一条命令启动、主要交互完整、数据可重置、类型检查和构建通过 |
| 功能可运行 | 真实接口、权限、持久化、错误处理和关键业务流程通过验证 |
| 项目可交付 | 配置完整、产物可追溯、迁移可执行、日志可定位、部署和恢复流程经过验证 |

第一版我建议交付一个完整的“客户管理”示例：包含登录、列表、搜索、分页、新增、编辑、详情和状态变更，同时具备 Mock 与真实后端。再用 QuizTest 中一个边界较清晰的管理模块验证存量接入流程。

这两个试点分别验收：**新项目从初始化到可演示能否顺利完成，以及旧项目接入规范后原有功能能否保持可用。** 验证通过后，再把成熟的模板、检查和部署能力固化为脚手架首版。
