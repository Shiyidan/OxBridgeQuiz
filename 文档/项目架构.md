# QuizTestDemo 项目架构

> **文档基线**：2026-07-17 代码现状
> **适用范围**：开发、测试、部署、数据迁移和后续功能扩展
> **说明**：本文以当前仓库和已部署环境为准，不再沿用早期 PostgreSQL、Redis、Tailwind 或“PDF 自动解析为唯一主流程”等旧设计描述。

## 一、项目定位与当前边界

QuizTestDemo 是面向 ESAT、TMUA、STEP 等考试的在线题库与测评系统，当前由学生端、管理后台和统一 API 服务组成。

当前核心能力包括：

- 用户名与密码注册、登录、资料维护和角色控制。
- 真题卷、AI 生成卷和模考卷的分类管理。
- 标准 JSON、JSON-in-Markdown 试卷导入、预览、编辑和发布。
- 考纲上传、启用、停用以及题目与考纲节点筛选。
- 试题库练习、诊断测试、答题进度保存、继续测试和交卷。
- 成绩计算、答题报告、错题本、练习记录和个人统计。
- 按考试类型配置会员权益、免费额度和后台手动授权。
- 用户管理、成本数据管理以及后台通用表格与分页。

当前功能边界：

| 状态 | 模块 |
|------|------|
| 当前主流程 | 标准试卷导入、真题库、试题库、考纲、在线答题、诊断测试、报告、错题本、会员权益、用户管理、成本管理 |
| 保留能力 | PDF/图片经 Qwen 解析、`Paper.questions` 旧字段兼容；旧随机诊断数据仅用于历史统计 |
| 尚未完成 | 支付订单与回调、OSS 文件存储、员工管理、正式订阅购买流程 |
| 后续基础设施 | CDN、Redis、SLB、多 ECS 高可用、OSS 版本与生命周期管理 |

PDF/图片识别代码仍保留在项目中，但当前标准化建设以 JSON 或 Markdown 导入并写入独立 `Question` 表为主。

## 五、前端架构

### 5.1 分层与依赖方向

```text
views 页面
  ├── components 通用组件
  ├── stores 全局状态
  └── api 业务请求模块
        └── utils/request.ts
              └── config.ts
```

约束如下：

- 页面不得直接散写 Axios 请求，统一调用 `src/api/` 中的业务函数。
- API 模块统一通过 `callApi<T>()` 发起请求，并直接接收统一响应包中的 `data`。
- `request.ts` 从 Pinia Auth Store 读取 Bearer Token，负责统一响应解包、`ApiError` 转换、错误提示和会话失效处理，不再保存独立 Token。
- 页面只通过 `ApiError.message/code/status` 或公共错误辅助函数处理业务分支，不依赖 Axios 的 `error.response` 内部结构。
- `config.ts` 负责 `local`、`test`、`prod` 和自定义 API 地址切换。
- 可复用状态进入 Pinia；仅页面内部使用的状态保留在页面组件中。

## 六、后端架构

### 6.1 分层与请求链路

```text
HTTP Request

  → requireAuth / requireAdmin
```

| `constants/` | 跨模块共享的业务枚举 |

### 6.3 统一响应与分页

所有 API 返回统一 envelope：

```ts
{
  success: boolean
  code: number | string
  errMsg: string
  data: T
}
```

- 成功使用 `code: 0`。
- 通用失败使用 `code: 1`。
- 业务错误可使用字符串错误码，例如 `AUTH_WRONG`。
- 前端响应拦截器在成功时只向业务层返回 `data`。

分页接口统一使用 `page` 和 `pageSize`，返回：

```ts
{
  list: T[]
  pagination: {
    page: number
    pageSize: number
    total: number
    totalPages: number
    hasPrev: boolean
    hasNext: boolean
  }
}
```

### 6.4 全局错误处理

API 的失败处理遵循以下顺序：

```text
业务 Router
  → createAsyncRouter() 捕获同步 throw 与 rejected Promise
  → 已知业务错误由路由按明确状态码返回
  → 未捕获异常进入 globalErrorHandler
  → 未匹配任何路由进入 notFoundHandler
  → fail() 生成统一 JSON envelope
```

- 所有承载业务处理的 Router 通过 `utils/asyncRouter.ts` 创建，Express 4 下的异步拒绝会显式调用 `next(error)`，不会成为未处理的 Promise rejection。
- `middleware/error.ts` 位于全部正常路由之后；不存在的接口返回 `404 + NOT_FOUND`，不再返回 Express 默认 HTML。
- 损坏 JSON 返回 `400 + INVALID_JSON`，请求体过大返回 `413 + PAYLOAD_TOO_LARGE`，上传文件过大返回 `413 + FILE_TOO_LARGE`。
- Zod 参数错误、Prisma 唯一键冲突和数据不存在分别映射为 422、409 和 404；未识别异常统一返回 `500 + INTERNAL_ERROR`。
- 服务端日志保留完整错误对象、请求方法和路径；客户端只收到允许公开的信息，未知异常不会暴露数据库结构、本地路径或调用堆栈。
- 请求入口生成服务端 Request ID，响应头 `X-Request-ID`、操作审计和单行 JSON 运行日志使用同一标识；管理员可从操作详情复制该值定位 PM2 日志。
- 如果响应头已经发送，错误处理器继续交给 Express 关闭或完成连接，避免重复写响应导致 `Cannot set headers after they are sent`。
- HTTP 全局错误处理中间件无法捕获定时 worker 和其他后台任务异常，这些入口仍必须显式使用 `.catch()` 并记录失败状态。

### 6.5 身份认证与基础安全

- 账号注册、登录和密码流程由认证模块统一处理，并通过邮箱验证码、密码哈希和模糊错误信息保护账号安全。
- 系统采用 Access Token 与可撤销 Refresh Session 组合：访问令牌仅保存在前端内存，刷新凭证通过 HttpOnly Cookie 管理。
- `requireAuth` 校验当前用户和会话状态，`requireAdmin` 在此基础上校验管理员角色。
- 登出、密码变更和会话轮换能够撤销服务端会话；认证相关接口配置频率限制。
- API 和 Nginx 共同承担安全响应头、缓存限制及生产端口收敛。

凭证有效期、哈希参数、Cookie 属性和验证码规则属于认证实现细节，以《3.3 登录模块技术方案》和运行配置为准。

| 内容 | `Paper` | 试卷元数据、来源类型和发布状态 |
| 内容 | `Question` | 官方题目主数据 |
| 内容 | `ParseTask` | PDF/图片解析任务状态 |
| 考纲 | `Syllabus` | 上传的完整考纲 JSON 和启用状态 |
| 考纲 | `SyllabusNode` | 启用考纲展开后的可查询节点树 |
| 用户 | `User` | 账号、角色、旧支付状态和备考偏好 |
| 权益 | `MembershipPlan` | 各考试类型的会员套餐定义 |
| 权益 | `UserMembership` | 用户按考试类型持有的会员记录 |
| 权益 | `EntitlementConfig` | 各考试类型的免费额度配置 |
| 答题 | `ExamRecord` | 一次套卷或题库练习记录 |
| 答题 | `AnswerRecord` | 每道题的作答、正确性和用时 |
| 诊断 | `DiagnosticSession` | 已下线随机诊断接口的历史会话，仅保留额度与统计兼容 |
| 运营 | `RevenueCost` | 成本项、金额、操作人和报销状态 |
| 审计 | `OperationLog` | 关键操作审计与学生行为统计的数据源 |

上表按业务领域列出主要模型；其中“答题”和“诊断”共同构成测评数据域。

### 7.2 关键关系

```text
Paper 1 ── N Question
Paper 1 ── N ParseTask
Paper 1 ── N ExamRecord

User 1 ── N ExamRecord
User 1 ── N DiagnosticSession
User 1 ── N UserMembership

ExamRecord 1 ── N AnswerRecord
Question 1 ── N AnswerRecord
```

### 7.3 题目主数据规则

- `Question` 是业务查询、考试、报告和错题本的唯一正式题目来源。
- `Paper.questions` 只保留为旧数据兼容和历史回填输入，新功能不得依赖它。
- 导入或编辑试卷中的题目必须通过 `syncPaperQuestions()` 同步到 `Question`。
- 题号和题目标识必须保持唯一，结构化字段通过 Prisma 按原生 JSON 写入。

具体 ID 生成方式、字段类型、JSON 结构和唯一索引属于数据库与导入规范，以《3.2 数据库构建》和《3.4 试卷上传解析技术方案》为准。

### 7.4 业务枚举

考试类型：

```text
ESAT / TMUA / STEP
```

试卷来源：

```text
realPaper  真题卷，进入诊断测试
mockPaper  模考卷，为仿真考试预留
aiPaper    AI 生成卷，进入试题库
```

主要状态：

```text
Paper.status: draft / published
User.role: student / admin
ExamRecord.status: in_progress / submitted
ExamRecord.phase: continuous / answering / paused / break / break_paused / ready_to_submit
UserMembership.status: active / expired / cancelled
MembershipPlan.plan: monthly / quarterly（历史订单可能保留 yearly）
```

枚举在后端 `constants/domain.ts` 和前端 `constants/` 中集中维护。

## 八、核心业务数据流

### 8.1 试卷导入、发布与分流

当前主流程：

```text
管理员选择 JSON 或 Markdown
  → 前端读取并预览标准结构
  → 后端 markdownValidator 校验与清洗
  → 创建 draft Paper
  → 生成纯数字 Paper.id
  → syncPaperQuestions 写入 Question
  → 管理后台预览与编辑
  → 发布为 published
  → 按 paperType 分流到学生端
```

标准导入结构为：

```text
{
  metadata: {
    paperName,
    examType,
    paperType,
    year,
    duration,
    totalQuestions
  },
  questions: [...]
}
```

发布后的分流规则：

| 条件 | 学生端入口 |
|------|------------|
| `status = published` 且 `paperType = realPaper` | 诊断测试列表 |
| `status = published` 且 `paperType = aiPaper` | 试题库 |
| `paperType = mockPaper` | 仿真考试预留，当前无完整学生端模块 |

PDF/图片模式当前仍可创建 `ParseTask` 并调用 Qwen 服务，但不是标准题目数据建设的首选入口。

### 8.2 诊断测试

```text
已发布 realPaper
  → 开始或重新测试时校验对应考试类型的诊断权益
  → 按“用户 + 考试类型”检查 activeDiagnosticKey，限制一个进行中诊断
  → 使用 ExamRecord 和 AnswerRecord 保存作答过程
  → 切页、锁屏或确认返回时原子保存并进入 paused，继续测试时恢复冻结的剩余时间
  → 正式提交时在事务内复核权益并释放 activeDiagnosticKey
  → 生成考试结果和诊断报告
```

只有正式提交的记录计入诊断使用量。重新测试复用正常开始接口并创建新的 `ExamRecord`，不得覆盖历史作答。重测资格由服务端根据当前用户、目标试卷、考试类型权益和进行中诊断占用实时判定，客户端不提供重测授权信息。测试状态、报告展示和异常容错以《4.8 诊断测试》和《4.8.1 诊断测试报告》为准。

#### 8.2.1 诊断报告版本边界

诊断报告以数据库快照中的 `reportVersion` 为事实版本，接口统一返回 `productVersion` 供前端选择渲染器：

- V1：历史只读兼容版本，不自动升级；用户主动点击“更新报告”后才基于原答卷生成 V2。
- V2：当前 ESAT/TMUA 新答卷的默认报告，统一使用确定性证据画像、受约束的模型分析和行动建议。
- 公共依赖：V1/V2 共用 `api/src/services/scoring.ts` 的评分标准、公共报告契约、版本注册和任务持久化逻辑，不在版本目录复制换算曲线。
- 前端结构：路由容器负责加载与版本选择，具体渲染器位于 `quiz-web/src/views/assessment/diagnostic-report/v1/` 和 `v2/`。
- 后端结构：V2 生成器位于 `api/src/services/diagnostic-report/v2/`，历史兼容边界与公共依赖说明位于同目录的 `README.md`。

### 8.3 试题库练习

```text
已发布 aiPaper
  → Question 进入题库候选集并按考纲等条件筛选
  → 校验对应考试类型的题库权益
  → 使用 ExamRecord 和 AnswerRecord 保存练习结果
  → 支撑结果详情、练习记录和错题本
```

题库筛选依赖当前启用的考纲数据。具体筛选、答题和空状态规则以《4.5 考纲管理》和《4.6 在线答题》为准。

### 8.4 结果、错题本与统计

- `ExamRecord` 保存整次练习或考试的开始、提交、题数和正确数。
- `AnswerRecord` 保存题目选择、是否正确、逐题用时和作答时间。
- 结果接口关联 `Question` 还原完整题目，并通过 `scoring.ts` 计算考试类型对应成绩。
- 错题本按用户聚合同一题的历史错误次数和错误选项，支持来源、难度、考纲和时间筛选。
- 个人中心统计来自已提交诊断记录和答题记录，不使用前端临时数据作为最终依据。

### 8.5 会员与额度

权益按 `examType` 独立计算：

- 诊断权限由 `Paper.accessTier` 与对应考试类型的有效 `UserMembership` 决定；免费卷不限重测次数，会员卷要求当前有效会员。
- 题库免费题量来自 `EntitlementConfig.questionBankLimit`；未配置时每种考试默认25题，试题库专项、自由组卷与练习本共用该额度。
- 有效 `UserMembership` 或管理员角色拥有对应考试类型的无限额度。
- 试题库消耗按已保存的 `AnswerRecord` 数量统计。
- 后台用户权限弹窗提交完整考试类型集合；未选中的当前或未来有效权益更新为 `cancelled`，全部清空即取消全部会员权益。
- 同一考试类型已有有效会员时，后台不会重复创建同类有效记录。

`UserMembership` 是学生会员权益的唯一正式数据源；用户基础表不保存全局付款状态。

### 8.6 考纲

```text
管理员上传考纲 JSON
  → 保存为 Syllabus.sourceJson
  → 启用时展开并覆盖该 examType 的 SyllabusNode
  → 题库和错题本根据节点及其后代 code 筛选题目
  → 停用时移除对应可查询节点树
```

每个考试类型同一时刻应以启用的考纲数据作为题库筛选依据。

### 8.7 学生用户行为分析

后台 `/admin/behavior-analytics` 基于业务考试记录与 `OperationLog` 实时聚合学生核心产品行为，不新增统计表或定时汇总任务。

```text
ExamRecord(status = submitted)
  → 按 Paper.paperType 区分诊断测试、试题库练习和模考练习
  → 按考试记录 ID 去重，统计完成次数、使用占比和学生偏好

OperationLog(action = diagnostic_report.view, result = success)
  → 统计成功读取诊断报告正文的次数
  → 不统计报告生成状态轮询和失败读取

OperationLog（通用操作审计）
  → 固定 actorRoleSnapshot = student 并排除 auth 认证登录模块
  → 按模块、action、actorUserId 与北京时间自然日聚合操作概览
  → 产品偏好、指标卡、模块排行、行为排行、每日趋势
  → 携带 role/module/action/time 下钻操作日志
  → 通过 Request ID 继续定位运行日志
```

- 学习活动完成次数使用 `ExamRecord.submittedAt` 作为发生时间，并只统计当前仍为学生角色的账号；操作与报告查看采用发生时的角色快照。
- 三类学习活动的使用偏好以完成次数最高者为准；周期内少于 3 次归为“数据不足”，最高次数并列归为“混合使用”。
- 报告查看率表示当期完成的诊断测试中，其报告在同一统计周期内被成功打开的比例；报告查看历史从该审计动作上线后开始积累，无法回填此前访问。
- 活跃人数仅按非空 `actorUserId` 去重；用户删除后遗留的空标识日志只计总操作次数，不计人均次数，并通过数据质量提示暴露。
- 登录、退出等 `auth` 操作不属于核心产品使用，避免认证频次掩盖资料、考试和支付模块的真实使用。
- 默认查询最近 30 个北京时间自然日，单次最多 90 天，并返回上一等长周期用于环比。
- 当前采用索引范围查询后在 API 进程实时聚合；若日志规模增长并出现明确慢查询，再评估复合索引或日汇总表。

## 九、配置、部署与备份

### 9.1 前端 API 配置

`quiz-web/src/config.ts` 支持：

- `VITE_API_ENV` 选择 `local`、`test` 或 `prod`。
- `VITE_API_BASE` 在确有需要时覆盖 API 地址。
- 本地 `test` 模式通过 Vite 将同源 `/api` 转发至测试后端，避免认证 Cookie 跨域失效。
- 测试部署与线上 `prod` 均使用同源 `/api`，由 Nginx 反向代理。

这种设计允许本地前端连接本地、测试或线上 API，但不得将生产密钥写入前端配置。

### 9.2 后端配置

`api/src/config.ts` 支持：

- `API_RUNTIME_ENV` 必须显式选择 `local`、`test` 或 `prod`，缺失时拒绝启动。
- `API_PORT`、`FRONTEND_URL`、`CORS_ORIGINS` 覆盖环境默认值。
- `DATABASE_URL` 提供 Prisma MySQL 连接串。
- `JWT_SECRET` 提供固定签名密钥。
- `EMAIL_CODE_SECRET` 提供固定验证码摘要密钥。
- `VISITOR_IP_HASH_SECRET` 提供网站访问 IP 的独立 HMAC 摘要密钥。
- `SMTP_USER`、`SMTP_PASS` 和 `MAIL_FROM` 提供邮件发送凭据。

`.env` 只保存环境相关配置和密钥，不进入 Git。测试和线上环境缺少固定 JWT、验证码密钥、访客 IP 摘要密钥或 SMTP 凭据时会拒绝启动；只有本地环境允许临时生成密钥。部署前使用 `API_ENV_FILE=/opt/quiz/api/.env npm run validate:runtime` 验证配置、数据库连接和 SMTP 登录。

### 9.3 部署方式

测试和线上环境采用原生单机部署：

```text
Nginx
  ├── Vue dist
  ├── /api → Express:3001
  └── HTTPS 证书

PM2
  └── api/dist/index.js

RDS MySQL
  └── Prisma migrate deploy
```

当前不使用 Docker。后端部署必须执行 Prisma migration，不使用 `prisma db push` 代替迁移历史。

### 9.4 备份

测试环境当前备份内容包括：

- RDS MySQL 逻辑备份。
- `/opt/quiz/uploads` 上传文件备份。
- 后端环境、PM2 和 Nginx 配置备份。
- manifest 与 checksum 校验记录。
- 部署前备份和每日定时备份。

正式环境还需在 RDS 控制台开启自动备份，并在接入 OSS 后补充对象版本、生命周期和异地备份策略。详细规则见 `文档/5. 部署方案/5.6 备份策略.md`。

## 十、架构约束与后续演进

### 10.1 当前必须遵守的约束

- 新题目业务只读写 `Question`，不得重新依赖 `Paper.questions`。
- 结构化 JSON 字段必须通过 Prisma 以数组或对象写入。
- 前端业务请求必须进入 `src/api/`，不得在页面散写请求实现。
- 角色、考试类型、试卷类型和会员状态必须使用集中常量。
- 管理写操作必须经过后端 `requireAdmin`，不能只依赖前端路由守卫。
- 数据库结构变更必须同时提交 Prisma schema、migration 和数据库文档更新。
- 生产 API、数据库和上传目录不得直接暴露到公网。
- 诊断测试的开始与重新测试必须由服务端根据权益、考试状态和 `activeDiagnosticKey` 判定；不得恢复或新增任何调试绕过参数。

### 10.2 下一阶段演进

1. 接入 OSS，替代 ECS 本地资料目录，同时保持现有 `storageKey` 和受控下载接口不变。
2. 完成支付订单、回调验签、会员开通与退款状态的数据闭环。
3. 备案通过后启用正式 DNS，完成外部 HTTPS、登录、上传和报告回归。
4. 将不再使用的独立诊断路径按产品结论清理。
5. 在访问量或可用性要求提升后，再评估 Redis、CDN、SLB 和多 ECS。
6. 完成员工管理和付费策略页面的真实业务实现，并补充教材库下载统计与批量管理。
